# Editor UI (`feature/`)

Guidance for the Compose UI layer. The graph editor lives in `feature/grapheditor/`; the workflow list, geofence, variables, apps, contacts, sound and permission screens are its siblings.

## The app's home

`HomeScreen` (`feature/home/`) is the `NavHost`'s start destination and the app's only tabbed screen: a Material 3 `NavigationBar` with **Workflows** (`WorkflowListScreen`) and **Setup** (`feature/setup/SetupScreen.kt`) above it. It is **one nav destination that swaps its own content**, not two destinations sharing a bar — the shape `EditorTabPanel` already takes, for the reason a bottom navigation bar exists at all: the bar stays put and the surface above it changes. Two destinations would additionally have made `MainActivity`'s slide transitions fire on every tab tap, where what they say is "you have left home for a screen of its own". `BackHandler` returns to Workflows from any other tab, and only from there does back leave the app.

The **Setup tab is where the ten shared screens live** — smart home, AI, mail, global variables, geofences, NFC tags, folder access, permissions, plugins, app access — grouped as Connections / Libraries / System. They used to hang off the workflow list's title row as two icon buttons and an eight-item overflow, which that file's comment had already declared full. The count was not really the problem: a dropdown shows nothing until it is opened, so a Home Assistant connection was something you had to already know was there. `SetupScreen` holds no state and every row calls straight through to a screen that did not change; the subtitles are static and say what a screen is *for*, because a count would mean wiring ten repositories in to say something the screen itself says on entry.

All ten wear the same header, and it is now **one composable rather than ten copies**: `SettingsTopBar` (`feature/SettingsTopBar.kt`), beside `BottomNavigationBar` and for its reason — the rule is the same rule on every one of those screens, so a copy can only drift. It already had. Eight of them agreed on a chrome `Surface`, a 60 dp row and an 18 sp title; App access and Plugins had drifted onto `titleLarge` and had lost `statusBarsPadding()`, so their titles sat *under* the status bar. The inset is consumed by the bar itself, because the bar is the topmost thing on every screen that uses it — and the list below takes `navigationBarsPadding()` for the same reason at the other end. The back button's content description stays a parameter: each screen names its own back action in its own string prefix.

The row the title gave up is a Material 3 `TopSearchBar` over the macro list, with `ExpandedFullScreenSearchBar` as its expanded half. **One `inputField` lambda is handed to both** — that is what moves the field between them rather than cross-fading two. The expanded rows are names and nothing else (`MacroSuggestionRow`, not `WorkflowRow`): this is a way to *find* a macro, and a mis-tap on `WorkflowRow`'s switch disarms one instead of opening it. The query is local `remember`, so switching tabs clears it — a filter you cannot see is worse than one you retype.

The bar itself is `BottomNavigationBar` (`feature/BottomNavigationBar.kt`), shared with the editor's — this screen supplies two items and nothing else. It was a full-height `NavigationBar` until 2026-08-26, on the argument that the editor's is squeezed to 64 dp because it sits over a canvas that wants every pixel and nothing here is under that pressure; the pressure was the wrong test, since the 16 dp between them is padding above and below the label and no screen in this app is saying more for having it. Both are the short one now, and the shared component — height, rule, palette, trimmed inset, 22 dp icon, 11 sp label — is what stops them drifting apart again, the way `SettingsTopBar` stops ten headers doing it.

## The editor's bottom bar

`EditorBottomBar` is a `BottomNavigationBar` under the canvas with three items: **Problems** (what the graph *is*), **Console** (what a run *did*) and **Variables** (what the state *is right now*, values ticking as a run writes them). The first two were top-bar icons and the third had nowhere to live at all; a fourth icon would have left the title about seventy dp again. Their badges are permanently visible on the bar, which is the point — a warning nobody can see until they open something is not a warning.

The shared component is a Material 3 **`ShortNavigationBar` rather than `NavigationBar`**: the same stacked icon-over-label item at 64 dp instead of 80, because nearly all the difference between the two is padding above and below the content. The component is still Material's, so the touch targets, ripple, selection pill and accessibility semantics are too. **Only the colours are overridden**, from `EditorColors`: the editor's palette is fixed dark and independent of the app theme, so a bar taking `MaterialTheme.colorScheme` would render *light* under a permanently dark canvas on any light-themed phone — and the home shell's bar shares that palette, so one override serves both.

The system's bottom inset is padding *inside* the bar, so it lands wholly below the labels and makes the bar read as bottom-heavy. `trimmedBottomInsets` (`feature/BottomNavigationBar.kt`, applied by the shared bar for both) keeps **half** of it when it is small enough to be a gesture handle — a handle is drawn over the app and the bar's own padding already clears it — and the whole of it otherwise, because a large inset is reserving real buttons that would swallow taps meant for the bar. The inset's size is what tells the two apart.

**It sits in the layout rather than over the canvas** — the last child of the editor's `Column`, so it covers no graph and intercepts no canvas touch. Its height never changes, so the region above is measured once. That region is `weight(1f)` and **not** `fillMaxSize()`, which would leave the bar measured to nothing. Nothing above the bar carries `navigationBarsPadding()` any more, because the bar pads itself for the gesture bar.

**The bar stays put and the surface above it changes**, which is what a bottom navigation bar means and the reason none of the three surfaces is a `Dialog`: a dialog window swallows every touch inside its bounds, so a bar left visible underneath one would be visible and dead. The selected tab is hoisted to `GraphEditorContent`, which composes `EditorTabPanel` **instead of** `EditorTopBar` + `CanvasRegion` in the same region — instead of, not over, because an overlay would have to swallow every pointer event to keep drags off the canvas gesture detectors, and leaving the canvas out of the composition is that guarantee for free (its transform lives in the ViewModel, so nothing is lost by putting it away). `CanvasRegion` is its own composable so that one move takes the Add FAB and the zoom controls with it — an Add Node button floating over the console is a button aimed at something you cannot see. The graph's other control, the Run button a `trigger.manual` card carries, is inside the canvas and goes away with it for free.

The swap is an **`AnimatedContent`** — rather than an `AnimatedVisibility` over a `Box`, because it drops the outgoing content when the transition ends, which is what keeps the "the canvas is not composed at rest" guarantee above while still showing it during the slide.

`surfaceTransition` (`EditorSurfaceTransition.kt`) is **two motions, because two different things are happening**. Leaving or returning to the graph is **vertical**: a surface rises over the canvas and drops back off the bottom, on `EditorOverlay`'s own tween, so "something has come up over what I was working on" reads the same everywhere in the editor — and only the moving half is animated, the canvas holding still, which is what makes it read as *over* rather than as a swap. Switching between surfaces is **horizontal**, following the order of the bar's items: tap something to the right of what is open and it comes in from the right. Nothing is being covered there — you are stepping along a row — and a surface that rose from the bottom each time would claim otherwise three times running.

`ContentTransform.targetContentZIndex` is load-bearing in the vertical cases and only there: on the way out the departing panel must stay above the canvas it is uncovering, and without it `AnimatedContent` draws the newly added content on top, so the panel slides down *behind* the canvas and simply vanishes.

Each surface carries a **`PanelTopBar`** that **replaces `EditorTopBar` rather than stacking under it**: the animated region is everything above the bottom bar, top bar included, so a surface rises over the whole screen bar the navigation items — the same gesture the full-screen overlays make, and the reason two stacked headers never arise. It therefore takes `EditorTopBar`'s own `BAR_HEIGHT` and `statusBarsPadding()` (`BAR_HEIGHT` is shared, not copied, because a mismatch would make the screen jump as a surface opened) and the same 6 dp / 12 dp insets, so the ✕ and the title land where the back arrow and the workflow name were. It holds the per-surface actions — Clear for the console, none for the other two. There are three ways back to the canvas: the ✕, tapping the selected bar item again, and system back.

A collapsed 44 dp strip that overlaid the canvas and could be **dragged** to half height was built here first and removed on 2026-08-03. Two things were wrong with it and both were structural: the strip had to stay small to be worth overlaying, which put it under Material's 48 dp minimum target; and the resize drag lived on that strip, directly over the bottom of the graph, so every pan started near the bottom edge resized the dock instead of moving the canvas. Overlaying only ever existed to make that drag affordable — a `Column` sibling would have re-measured the canvas every frame of it. With no drag there is nothing to overlay for, and `EditorOverlay`'s rejection of bottom sheets stands untouched rather than being relitigated.

`ConsoleBody`, `ProblemsBody` and `VariablesBody` (in `ConsolePanel.kt` / `ProblemsPanel.kt` / `VariablesPanel.kt`) are the three surfaces, each filling the region and collecting its own flows. Variables shows only the *list* — creating and editing open the full-screen `VariableEditorOverlay` the picker opens, because this region stops above the bar and the keyboard would take most of what is left.

**Variables shows one scope at a time**, and is the one surface with a second level. It lists *this workflow's* declarations only; the shared library is behind a row `VariableList` draws for `onOpenGlobals`, carrying the global count so the shared set is represented on the screen without being listed on it. Listing every global under a macro's own two counters makes the macro look like it has fifteen — and the picker, where the question is "which of my variables is this?", still shows both sections for the opposite reason.

That second level lives **inside the editor** rather than routing to the standalone globals screen, and the back gesture is why: leaving the editor and coming back would land on the canvas, whereas back from the globals has to return to the workflow's own variables. So `EditorTabPanel` holds a `showingGlobals` flag with its own `BackHandler`, registered below `GraphEditorContent`'s so the dispatcher offers it the gesture first. `PanelTopBar`'s leading button carries which of two things it does — ✕ leaves for the graph, ← goes back a level — since it is the same button and the icon is the only thing that says which.

## A macro's own actions, in one menu

Edit, Add to home screen, Duplicate, Export, Share, Delete — the six things done to a macro *as a whole* — are **`MacroActionsMenu`** (`feature/macro/`), opened both by a `WorkflowRow`'s ⋮ and by `EditorTopBar`'s. They were two menus until 2026-08-26: six items on the list row, two in the editor, which made the editor the one place a macro could be looked at but not sent to anybody — and the editor is exactly where somebody is standing when they decide a macro is finished. One composable now, so the next item added appears in both.

What each item *does* is likewise one implementation, **`MacroOperations`** (`feature/macro/`), which both ViewModels delegate to: a Duplicate that re-mints credentials on one screen and not on the other is not a difference any user could predict. The document-picker round trip (`rememberMacroExport`) and the whole pin flow with its two dialogs (`rememberMacroPinner`) are shared the same way, because each is state plus a launcher that a screen offering the item has nothing to say about.

Two differences are real and stayed. **Deleting** is each screen's own — the editor has a debounced save and an `isDeleted` flag to stand down first, the list has neither. And the editor has **a graph in memory that is newer than the file**: every one of these actions reads the macro back through the repository, so `EditorMacroActions` flushes first. Without that, exporting thirty seconds into a session writes the graph as it was when the last keystroke settled — silently, into a file the user is about to send somebody.

Two things are deliberately *not* in the menu. **Arming** is a switch beside it in both places, because it is flipped repeatedly and has to say its state without being opened. **Import** belongs to the list rather than to any one macro, so it sits by the Add FAB.

## The AI assistant

`AssistantOverlay` (`feature/grapheditor/assistant/`) is the editor's fourth surface and the only one that is **not** one of the bottom bar's. It is **one panel whose conversation folds**, with a drag handle on top: handle, conversation (transcript + model chip), status row, input. A small FAB above Add Node opens it.

**It is over the canvas rather than instead of it, and that is the whole reason it is not a bottom-bar surface.** The three surfaces above replace the canvas because none of them is about the graph as it is right now; this one is, because the model's edits land **live** — nodes appear as they are made and the canvas auto-follows whatever was just touched, until the first pan or zoom hands it back to the user for the rest of the turn (`GraphEditorViewModel.canvasMovedByUser`, `focusOn`). A surface that put the canvas away would be an assistant you cannot watch.

**Only the conversation folds. The handle, the status row and the input never move.** That is what makes the input consistent: the same field in the same place whether the panel is folded, open, or mid-turn, so there is no moment where the thing you were typing into is gone. It was two composables swapped by an `AnimatedContent` first, and that could not be made smooth — a swap is not one thing moving, and it took the input with it.

**The input also wins the space.** The conversation is the panel's only weighted child, and in a `Column` the weighted children are measured **after** the rest — so the handle, the status row and the input are measured first and get the height they ask for, and the conversation takes what is left (`fill = false`, so it may take less). Without that the conversation was measured first, ate the panel, and squeezed the input down to a single line exactly when there was most to type about. `Modifier.folding` therefore drops only the *minimum* height it is given and keeps the maximum: measuring past what the `Column` left over would take the space straight back.

**The fold is continuous, not a toggle.** An `Animatable` fraction is snapped to wherever the finger is during a drag and animated to an end on release, settling by position unless the gesture was a flick. `Modifier.folding` does three things at once, each load-bearing: measures the content with **unbounded height** so the natural size is the content's own (a two-line conversation opens to two lines, not to a fixed box with a gap); **places from the bottom** so folding hides the oldest message and the newest stays against the input; and reads the fraction **in the measure phase**, so a fold re-measures rather than recomposing. The scrim's alpha is the same fraction read in the **draw** phase, which is why the dimming follows the finger and costs no recomposition.

`draggable` rather than `detectVerticalDragGestures`, for the one thing the raw detector does not give: a velocity in `onDragStopped`.

**The handle row carries the two buttons that end things**, mirrored across the grabber: ↺ starts a new conversation, ✕ closes the assistant. `restart()` drops the transcript, the draft and the undo snapshot and **leaves the graph alone** — that is the whole distinction from `undo()`. It earns its place because the transcript is restated in every prompt, so an exchange that went somewhere unhelpful goes on costing tokens and steering answers until it is cleared. It is refused mid-turn rather than cancelling: stopping the model is the ✕ on the status row, and one button that sometimes also aborts a billed call is one button too many.

**`AssistantFab` wears a running border while a turn is in flight** (`feature/grapheditor/assistant/AssistantFab.kt`). It is the only assistant control still on screen once the panel is folded away or closed, and a turn goes on running either way — nodes appear on the canvas with nothing saying who is placing them. The border is drawn as a **filled, rotating sweep gradient behind an opaque button**, clipped to a rounded rectangle: a stroke would have to be rotated to move its gradient, and rotating a rounded rectangle spins its corners. Here the clip fixes the silhouette, the fill rotates inside it so only the colour travels, and the button's own container covers the middle. It is composed only while busy, so the infinite animation does not exist at rest.

**Focusing the input unfolds it**, because going to type is going to want to see what has been said. On focus rather than on each keystroke: a fold made while the field is focused is deliberate, and re-opening on the next character would make it impossible to hold.

**The margin around the panel goes when the keyboard comes up; the padding inside it does not.** They are different things: the margin exists to hold the panel off the bottom bar, and with a keyboard there the bar is not what is underneath any more. `imePadding()` is applied *outside* the margin so the margin is genuinely what sits below the panel, and the margin keys on `WindowInsets.isImeVisible` rather than on field focus — back dismisses the keyboard before reaching any `BackHandler`, which leaves the field focused with the bar below again.

**That only works because the canvas region consumes the bar's height.** The window is `enableEdgeToEdge` plus `adjustResize`, so it does *not* shrink for the keyboard — the IME arrives as an inset measured from the window bottom. The bottom bar is a **sibling** of the canvas region, so nothing in that region knows the window does not end where the region does, and an `imePadding()` inside it adds the whole keyboard height and lands the panel one bar-height above the keyboard. `GraphEditorContent` therefore measures the bar (`onSizeChanged`) and hands the region a `consumeWindowInsets(bottom = barHeight)`, which is what makes an inset applied in there mean what it says. Anything else in that region that ever needs the IME inherits the fix.

**Three gestures fold it away and none of them closes it**: the handle dragged down, the handle tapped, and a tap on the scrim. A tap outside is aimed at the canvas the panel is covering, so it minimizes — a conversation is not something a stray touch should throw away. Back does the same first and only closes on the second press, which is the order the selection handler above already follows. Closing is the ✕ on the handle row.

**The draft lives in `AssistantState`, not in the input.** Folding must not destroy a half-written question — that gesture exists precisely so you can go and look at the canvas while writing one.

**It is in the layout tree and not a `Dialog`.** `EditorOverlay` is a `Dialog` precisely so touches cannot fall through to the canvas, which is the opposite of what the folded state needs. The scrim can instead be switched off, and can answer a tap by folding away rather than by closing.

**It does not resurrect the collapsed dock removed on 2026-08-03.** That strip failed for two structural reasons: it was permanent chrome that had to stay under Material's 48 dp target to be worth overlaying, and its resize drag sat over the bottom of the graph so every pan started near the bottom edge resized it. This is composed only while the assistant is open, and its handle is a full row on the panel's own **top** edge rather than a hairline between the panel and the canvas.

**The ✕ on the handle row is bigger than the app's other small icon buttons, and it grew out of `IconButton`'s padding rather than out of the row.** The button fills the row's height and carries a larger glyph; the row and the grabber are unchanged. A grabber is a marking that says the panel moves rather than a thing to aim at, and the whole row takes the drag anyway — so enlarging it would have cost height for nothing.

**Layout is automatic by default and the model can override it per node.** `GraphLayout.arrange` lays out what a turn *added*, and `move_node` is for tidying what that cannot decide — which branch of an `action.if` goes on which side, or a graph the user asked to have cleaned up. A `GraphEdit` therefore reports `movedNodes` beside `addedNodes`, and the session arranges `added - placed`: arranging a node the model positioned would undo `move_node` a moment after it ran. `read_graph` reports every node's position, without which there is nothing to lay out against, and a coordinate beyond `MAX_COORDINATE` is refused — a card at `1e9` is gone as far as anyone can tell, which is worse than being told the number was rejected.

**A turn states no reply limit of its own, and that is what makes the limit reachable.** `AiRequest`'s 1024 default is sized for a *macro* firing unattended, where a runaway answer spends quota with nobody watching — neither half describes this, and a turn additionally spends its budget on **tool calls** before a word of the answer is written, so it ran out mid-build with "the reply was cut off before any text was produced — raise the reply limit", advice aimed at a config field this surface has not got. The number now lives on `AiModelProfile.maxOutputTokens`, edited beside the model it applies to; a constant in the session would have fixed the size and left it just as unreachable.

`replyLimit` (`data/ai/RoutingAi.kt`) resolves it, and the precedence is the **opposite** of `combineInstructions`' for the opposite reason: two system prompts combine because a persona and a task are both true at once, where two numbers cannot both hold and the specific one has to win. So a node's own "Longest reply" field beats the profile, the profile governs anything with no such field, and `AiRequest.DEFAULT_MAX_OUTPUT_TOKENS` is the floor under both. If the profile overrode the node, raising the assistant's room would quietly multiply what every macro on that key may spend.

**Leaving mid-turn does not stop the turn**, and `isExpanded` persisting across close and open is what makes coming back land folded rather than open over a running call — no second piece of state remembers it. The status row's ✕ says the result has been *read* and clears it without leaving; the handle's ✕ leaves and keeps an unread result for next time.

`AssistantSession` holds the conversation and lives on the ViewModel, not in the composition — an AI call takes tens of seconds and is billed, and a rotation is the worst possible moment to lose one. It talks to the editor through `AssistantEditor`, a deliberately short interface that is the whole list of what an AI turn can reach.

**Every string the user reads is a resource; every string the model reads is not.** The tool descriptions, the standing instruction and the node catalogue are English constants in `engine/ai/`, on the run log's reasoning — a model reads those. So the pill is handed a tool name and a typeId rather than a sentence, and words it here through `NodeText`; and the five things the app itself says are an `AssistantNotice` enum rather than text, so they resolve from `strings_assistant.xml` like everything else.

`arm()` hands `WorkflowRunner` a *snapshot* loaded from disk, so an edit to an armed macro takes effect only on re-arm. The editor drives that itself: saves are debounced (`SAVE_DEBOUNCE_MS`, flushed from `onCleared` on `ServiceLocator.appScope` so the last edit survives the back gesture), and a save sends `ACTION_RELOAD` when `Workflow.runtimeSignature()` changed. That signature omits `x`/`y`/node `name`/`visibleDataInputs`, so dragging a node never re-arms — re-arming re-registers geofences and re-enqueues periodic work. `ACTION_RELOAD` re-arms only an already-armed macro and passes `announceEnabled = false`, so `trigger.macro_enabled` does not re-fire on every edit.
