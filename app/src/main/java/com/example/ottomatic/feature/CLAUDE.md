# Editor UI (`feature/`)

Guidance for the Compose UI layer. The graph editor lives in `feature/grapheditor/`; the workflow list, geofence, variables, apps, contacts, sound and permission screens are its siblings.

## The app's home

`HomeScreen` (`feature/home/`) is the `NavHost`'s start destination and the app's only tabbed screen: a Material 3 `NavigationBar` with **Workflows** (`WorkflowListScreen`) and **Setup** (`feature/setup/SetupScreen.kt`) above it. It is **one nav destination that swaps its own content**, not two destinations sharing a bar — the shape `EditorTabPanel` already takes, for the reason a bottom navigation bar exists at all: the bar stays put and the surface above it changes. Two destinations would additionally have made `MainActivity`'s slide transitions fire on every tab tap, where what they say is "you have left home for a screen of its own". `BackHandler` returns to Workflows from any other tab, and only from there does back leave the app.

The **Setup tab is where the ten shared screens live** — smart home, AI, mail, global variables, geofences, NFC tags, folder access, permissions, plugins, app access — grouped as Connections / Libraries / System. They used to hang off the workflow list's title row as two icon buttons and an eight-item overflow, which that file's comment had already declared full. The count was not really the problem: a dropdown shows nothing until it is opened, so a Home Assistant connection was something you had to already know was there. `SetupScreen` holds no state and every row calls straight through to a screen that did not change; the subtitles are static and say what a screen is *for*, because a count would mean wiring ten repositories in to say something the screen itself says on entry.

All ten wear the same header, and it is now **one composable rather than ten copies**: `SettingsTopBar` (`feature/SettingsTopBar.kt`), beside `trimmedBottomInsets` and for its reason — the rule is the same rule on every one of those screens, so a copy can only drift. It already had. Eight of them agreed on a chrome `Surface`, a 60 dp row and an 18 sp title; App access and Plugins had drifted onto `titleLarge` and had lost `statusBarsPadding()`, so their titles sat *under* the status bar. The inset is consumed by the bar itself, because the bar is the topmost thing on every screen that uses it — and the list below takes `navigationBarsPadding()` for the same reason at the other end. The back button's content description stays a parameter: each screen names its own back action in its own string prefix.

The row the title gave up is a Material 3 `TopSearchBar` over the macro list, with `ExpandedFullScreenSearchBar` as its expanded half. **One `inputField` lambda is handed to both** — that is what moves the field between them rather than cross-fading two. The expanded rows are names and nothing else (`MacroSuggestionRow`, not `WorkflowRow`): this is a way to *find* a macro, and a mis-tap on `WorkflowRow`'s switch disarms one instead of opening it. The query is local `remember`, so switching tabs clears it — a filter you cannot see is worse than one you retype.

`trimmedBottomInsets()` lives in `feature/BottomBarInsets.kt` and is shared by this bar and the editor's; the rule below is its rule, and it is one rule rather than two.

## The editor's bottom bar

`EditorBottomBar` is a Material 3 `ShortNavigationBar` under the canvas with three items: **Problems** (what the graph *is*), **Console** (what a run *did*) and **Variables** (what the state *is right now*, values ticking as a run writes them). The first two were top-bar icons and the third had nowhere to live at all; a fourth icon would have left the title about seventy dp again. Their badges are permanently visible on the bar, which is the point — a warning nobody can see until they open something is not a warning.

**`ShortNavigationBar` rather than `NavigationBar`**: the same stacked icon-over-label item at 64 dp instead of 80, because nearly all the difference between the two is padding above and below the content. The component is still Material's, so the touch targets, ripple, selection pill and accessibility semantics are too. **Only the colours are overridden**, from `EditorColors`: the editor's palette is fixed dark and independent of the app theme, so a bar taking `MaterialTheme.colorScheme` would render *light* under a permanently dark canvas on any light-themed phone.

The system's bottom inset is padding *inside* the bar, so it lands wholly below the labels and makes the bar read as bottom-heavy. `trimmedBottomInsets` (`feature/BottomBarInsets.kt`, shared with the home shell's bar) keeps **half** of it when it is small enough to be a gesture handle — a handle is drawn over the app and the bar's own padding already clears it — and the whole of it otherwise, because a large inset is reserving real buttons that would swallow taps meant for the bar. The inset's size is what tells the two apart.

**It sits in the layout rather than over the canvas** — the last child of the editor's `Column`, so it covers no graph and intercepts no canvas touch. Its height never changes, so the region above is measured once. That region is `weight(1f)` and **not** `fillMaxSize()`, which would leave the bar measured to nothing. Nothing above the bar carries `navigationBarsPadding()` any more, because the bar pads itself for the gesture bar.

**The bar stays put and the surface above it changes**, which is what a bottom navigation bar means and the reason none of the three surfaces is a `Dialog`: a dialog window swallows every touch inside its bounds, so a bar left visible underneath one would be visible and dead. The selected tab is hoisted to `GraphEditorContent`, which composes `EditorTabPanel` **instead of** `EditorTopBar` + `CanvasRegion` in the same region — instead of, not over, because an overlay would have to swallow every pointer event to keep drags off the canvas gesture detectors, and leaving the canvas out of the composition is that guarantee for free (its transform lives in the ViewModel, so nothing is lost by putting it away). `CanvasRegion` is its own composable so that one move takes the Add FAB and the zoom controls with it — an Add Node button floating over the console is a button aimed at something you cannot see. The graph's other control, the Run button a `trigger.manual` card carries, is inside the canvas and goes away with it for free.

The swap is an **`AnimatedContent`** — rather than an `AnimatedVisibility` over a `Box`, because it drops the outgoing content when the transition ends, which is what keeps the "the canvas is not composed at rest" guarantee above while still showing it during the slide.

`surfaceTransition` (`EditorSurfaceTransition.kt`) is **two motions, because two different things are happening**. Leaving or returning to the graph is **vertical**: a surface rises over the canvas and drops back off the bottom, on `EditorOverlay`'s own tween, so "something has come up over what I was working on" reads the same everywhere in the editor — and only the moving half is animated, the canvas holding still, which is what makes it read as *over* rather than as a swap. Switching between surfaces is **horizontal**, following the order of the bar's items: tap something to the right of what is open and it comes in from the right. Nothing is being covered there — you are stepping along a row — and a surface that rose from the bottom each time would claim otherwise three times running.

`ContentTransform.targetContentZIndex` is load-bearing in the vertical cases and only there: on the way out the departing panel must stay above the canvas it is uncovering, and without it `AnimatedContent` draws the newly added content on top, so the panel slides down *behind* the canvas and simply vanishes.

Each surface carries a **`PanelTopBar`** that **replaces `EditorTopBar` rather than stacking under it**: the animated region is everything above the bottom bar, top bar included, so a surface rises over the whole screen bar the navigation items — the same gesture the full-screen overlays make, and the reason two stacked headers never arise. It therefore takes `EditorTopBar`'s own `BAR_HEIGHT` and `statusBarsPadding()` (`BAR_HEIGHT` is shared, not copied, because a mismatch would make the screen jump as a surface opened) and the same 6 dp / 12 dp insets, so the ✕ and the title land where the back arrow and the workflow name were. It holds the per-surface actions — Clear for the console, none for the other two. There are three ways back to the canvas: the ✕, tapping the selected bar item again, and system back.

A collapsed 44 dp strip that overlaid the canvas and could be **dragged** to half height was built here first and removed on 2026-08-03. Two things were wrong with it and both were structural: the strip had to stay small to be worth overlaying, which put it under Material's 48 dp minimum target; and the resize drag lived on that strip, directly over the bottom of the graph, so every pan started near the bottom edge resized the dock instead of moving the canvas. Overlaying only ever existed to make that drag affordable — a `Column` sibling would have re-measured the canvas every frame of it. With no drag there is nothing to overlay for, and `EditorOverlay`'s rejection of bottom sheets stands untouched rather than being relitigated.

`ConsoleBody`, `ProblemsBody` and `VariablesBody` (in `ConsolePanel.kt` / `ProblemsPanel.kt` / `VariablesPanel.kt`) are the three surfaces, each filling the region and collecting its own flows. Variables shows only the *list* — creating and editing open the full-screen `VariableEditorOverlay` the picker opens, because this region stops above the bar and the keyboard would take most of what is left.

**Variables shows one scope at a time**, and is the one surface with a second level. It lists *this workflow's* declarations only; the shared library is behind a row `VariableList` draws for `onOpenGlobals`, carrying the global count so the shared set is represented on the screen without being listed on it. Listing every global under a macro's own two counters makes the macro look like it has fifteen — and the picker, where the question is "which of my variables is this?", still shows both sections for the opposite reason.

That second level lives **inside the editor** rather than routing to the standalone globals screen, and the back gesture is why: leaving the editor and coming back would land on the canvas, whereas back from the globals has to return to the workflow's own variables. So `EditorTabPanel` holds a `showingGlobals` flag with its own `BackHandler`, registered below `GraphEditorContent`'s so the dispatcher offers it the gesture first. `PanelTopBar`'s leading button carries which of two things it does — ✕ leaves for the graph, ← goes back a level — since it is the same button and the icon is the only thing that says which.

`arm()` hands `WorkflowRunner` a *snapshot* loaded from disk, so an edit to an armed macro takes effect only on re-arm. The editor drives that itself: saves are debounced (`SAVE_DEBOUNCE_MS`, flushed from `onCleared` on `ServiceLocator.appScope` so the last edit survives the back gesture), and a save sends `ACTION_RELOAD` when `Workflow.runtimeSignature()` changed. That signature omits `x`/`y`/node `name`/`visibleDataInputs`, so dragging a node never re-arms — re-arming re-registers geofences and re-enqueues periodic work. `ACTION_RELOAD` re-arms only an already-armed macro and passes `announceEnabled = false`, so `trigger.macro_enabled` does not re-fire on every edit.
