# Waiting mid-run, and the fork it needs

### Waiting mid-run, and the fork it needs

Waiting for a *duration* is `action.delay` and blocks its one `out`. Waiting for a **moment** is `action.wait_until`, and it cannot block, because "at 22:00, turn the lights off" is almost never the only thing a macro wants to do when it starts. So it is a **`ForkAction`** (`engine/NodeContracts.kt`) — the third shape the executor drives itself, after the two loops, and for the same reason: a `NodeOutput.route` is a *choice* between outputs, and this is not a choice. Both fire, at different times.

`ExecOutputs.FORK` keeps the immediate branch named **`out`**, following `ACKNOWLEDGED`'s "the plain `out` is deliberately first and deliberately unrenamed" — a fork is wired in exactly where a plain action was, so nothing saved is stranded if a node ever grows a second branch. Only the *label* changes ("Carry on now" / "When the time comes"), because unlike `out` beside `timed_out`, both of these mean "go" and wiring the wrong one is the whole mistake to design against. `ExecutionRoute.CONTINUE` therefore shares `ExecPorts.OUT` with `ExecutionRoute.OUT`, which is safe only because nothing maps a port name back to a route.

**The deferred branch must not be awaited.** `coroutineScope` around it is the obvious implementation and it is wrong in three places none of which are visible from the executor: `WorkflowRunner.collect` is a sequential `flow.collect`, so an eight-hour wait swallows every event the trigger fired meanwhile; `trigger.macro_finished` comes from `runFromTrigger`'s `finally`; and a widget tile sits on "Running…" until `runFromTrigger` returns. So it is launched on a scope that outlives the run, and the one with the right lifetime is the **arm** — `WorkflowRunner.run`'s `supervisorScope`, cancelled by a disarm, cancelled-and-joined by a re-arm, and by nothing else. `runFromTrigger`'s `deferredScope` is nullable and null means *run it inline*, which is what makes the executor's own tests deterministic without a test dispatcher.

The **manual/widget path has no arm**, so it passes `ServiceLocator.appScope` instead — the honest owner when the switch may well be off — and `MacroEngineService.runManual` then holds the foreground service up until the wait is done (`stopIfIdle`, `PendingWaits.count`). Without that the service stops itself the moment nothing is armed and takes the second half of the macro with it.

`Run.fork()` copies `dataCache` and `onPath`, and needs to for two independent reasons. `pulse`'s `finally` removes the fork node once `runFork` returns, so a **shared** `onPath` would leave the deferred branch unguarded and a `resumed` wire reaching back would recurse until the stack gave out. And the deferred branch runs hours later: "it sees the graph as it was at the fork" is the only rule that can be explained. The copy is also what makes the two branches safe to walk in parallel, which on the service's `Dispatchers.Default` they genuinely are. `Item` is immutable, so it is shallow. A fork inside a loop body is the case where the snapshot earns it: iteration 3's branch fires after the loop has moved on, and only its own copy still carries iteration 3's index.

That snapshot is also why **`GraphValidator.validateForkBranches`** exists. `validateStrictDataSemantics` walks raw exec edges, in which both fork outputs are ordinary forward edges — so a wire from the `out` branch into the `resumed` branch passes, then reads nothing at runtime and quietly substitutes the consumer's form value, which is the one thing that rule exists to prevent. It is an ERROR blocking the consumer, in both directions, and a node reachable from *both* ports is excluded: that is a diamond, which already runs once per incoming pulse.

Two costs are written into the nodes' own KDoc rather than left to be discovered: a `Stop Macro` downstream of `out` cancels a wait that has not fired but cannot un-run a branch that has, and a pending wait **does not survive process death** — alarm-backed means it survives *doze*, not a restart. The durable "at 07:00 tomorrow, do X" is `trigger.schedule`, re-armed from disk on every boot. `MAX_PENDING_WAITS` caps the pending branches process-wide (a `Repeat 1000` would otherwise arm a thousand platform alarms), announced in the run log the way `MAX_ITERATIONS` is.

**Waiting itself goes through `Waits`** (`core/service/`, Android half in `data/wait/`), because `kotlinx.coroutines.delay` measures *scheduler* time and does not advance while the CPU is suspended — an overnight wait resumed whenever the phone next woke. `AndroidWaits` arms the same `setExactAndAllowWhileIdle` alarm `trigger.schedule` uses (shared through `data/trigger/ExactAlarms.kt`) and **races it against a wall-clock sleep**, taking whichever lands first: the fallback can only ever fire *late*, so the alarm wins under doze and the sleep wins when an OEM drops the alarm. Its `PendingIntent` is keyed on a **per-wait token, not a node id** — the executor supports overlapping runs by design and a wait in a loop multiplies that, so a node-keyed one would collapse two waits onto one alarm under `FLAG_UPDATE_CURRENT`. `awaitUntil` takes the caller's continuation as a *block* so the wake lock covers the resumed walk, which is long after `onReceive` gave its own up. `action.delay` routes through the same facade, which fixed the identical drift bug in it for one line.

`action.wait_until` is the first node to declare `EXACT_ALARM`, which moved that row out of `PermissionCatalogue.appLevel` into the node half — the derivation CLAUDE.md already described, doing what it was built to do, and forced by `PermissionCatalogueTest`'s "nothing is in both" invariant. `trigger.schedule` has the identical degradation and still declares nothing; declaring it there is the obvious follow-up. The day filters are shared with that trigger through `DayFilter` (`domain/model/`), on `TimeOfDay`'s reasoning: two nodes answering "which day is this?" separately would eventually disagree.

`arm`/`disarm`/`rearmAll` are read-modify-writes of `activeJobs` spanning suspension points, so **every caller must hold `armMutex`**. Without it two overlapping arms of the same id each find no previous entry, each start a runner, and each store into the map — orphaning a runner that keeps collecting its triggers against a stale graph and is no longer cancellable by anything, including a disable/enable cycle. Both also `cancel()` **and `join()`** the previous job: trigger teardown runs in a `finally` that releases a platform resource keyed by node id, so an un-awaited cancel can tear down what the next arm just registered.
