# Variables

`action.set_variable` writes and `value.variable` reads the graph's **only writable state** — `VariableStore` (`data/trigger/`), persisted to `{filesDir}/variables.json`, behind the `Variables` facade. Everything else in the graph is derived from what is true right now, which covers "when I get home, turn the lights on" and not "the third time this happens today"; scripting does not close that gap, because every isolate starts empty.

`trigger.variable_change` already existed and could never fire, because nothing wrote to the store. It fires now. Writing an unchanged value is a deliberate no-op — "when this changes" must not mean "whenever anyone looked".

**A variable is declared before it is used.** A `VariableDeclaration` (`domain/model/`) carries an id, a name, a `ValueType`, an initial value and a `constant` flag; every node that touches one holds a *reference* chosen from a picker (`@Picker(PickerKind.VARIABLE)`), never a typed name. Before this, a variable existed the moment some node wrote a name into it, so a typo silently named a *different* variable that read as unset and looked like a broken node — and nothing in the app could say what a macro remembered. Declaring makes the typo unmakeable and makes a reference to something deleted a `WARNING` the Problems panel can raise.

**Two scopes.** A workflow's own declarations live in `Workflow.variables`; the shared ones live in `{filesDir}/variables/globals.json` via `GlobalVariableRepository`. Locals are in the workflow because everything that resolves one already holds it — `effectivePorts` takes it, `GraphValidator` takes it, `arm()`'s snapshot is one, the editor's debounced save writes it, and deleting the macro takes them with it like the run log. Globals have no such carrier, so they are published to `GlobalVariables` (`domain/registry/`), a hydrated object: `effectivePorts` is a pure function called from Compose *layout*, so it can have neither a suspension point nor a repository. Threading a parameter instead would have touched ~40 call sites to avoid one `@Volatile` field.

**References are ids, keys carry the scope.** `VariableRef` (`domain/model/`) parses the persisted spec exactly as `ValueSource` parses `val:<typeId>`: `g:<id>` is global, a bare `<id>` is local, and blank is *nothing chosen* — a real state a fresh node has, which is why `parse` returns null where `ValueSource.parse` falls back. The **store key** is a different string (`g:<id>` / `w:<workflowId>:<id>`): a spec must not embed a workflow, or copying a workflow would have to rewrite its own config values, while a key must, so a deleted macro's values can be swept by prefix. Ids rather than names is the `GeofencePlace` trade — renaming is then free in both scopes and never reaches into another workflow's file. The cost is that an id is unreadable, so every log line and every trigger payload resolves the declaration and prints the *name*.

**Binding happens once per arm.** `WorkflowRunner.run` is the only place holding a `Workflow` *and* building the executor *and* activating the triggers, so it wraps both: `context.boundTo(workflow)` gives every node a `BoundVariables` that resolves refs, and `BoundTriggerHost` scopes `variableChanges` on the way in and puts the display name back on the way out (`VariableChangeTrigger` needs no change at all). `BoundVariables`' wrapper **must override `scoped`** — `DefaultExecutionContext`'s own `Scoped` re-wraps the *original* delegate, so the generated `by delegate` forwarder would discard the binding for every action the executor runs, silently and at runtime only. `BoundVariablesTest` pins it.

A **constant** refuses `set` and is never stored at all, so it cannot drift from its own declaration. Initial values seed **lazily on read**, not at arm: seeding eagerly would fire `trigger.variable_change` for every declared variable on every edit that re-arms, which is the rule the store's own `set` exists to keep. `Variables.set` returns a three-state `VariableWrite` rather than a `Boolean` because "that is a constant" and "nothing is declared there any more" send the user to two different places. The store itself never refuses: it is a keyed map with an event hub attached, and everything that makes a variable *declared* lives one layer up.

**What is stored is still flat text.** A declaration's `ValueType` is the same one `transform.convert` and `@Ports` already offer, not a second type system beside `ItemSchema`, and it governs what may be **connected**, never what is **stored** — `NodeSchema.decode` still flattens a wired value through `asText()`. What it buys is that `value.variable` hands back a typed item and `action.set_variable`'s `value` port is type-checked, so a counter drops into a numeric port with no `transform.convert` in the wire and a number wired at a text variable is a refused drop. That is the one place `ValueType.convert` runs off-canvas, and it is safe for the reason the totality rule asks for: **the declaration is the visible artefact**. Lists are unchanged — `action.list_add` stores the array's JSON text and `transform.json_read` reads it back, so `VariableStore` still has no idea what a list is (see **Lists and iteration**).

**Migration, without a schema bump.** `CURRENT_SCHEMA_VERSION` is deliberately not raised: `WorkflowRepository.load` gates on `>=` and *discards* older files, so bumping would destroy every existing macro, and a defaulted field with `ignoreUnknownKeys` makes it unnecessary. Instead `repairVariableRefs` (`domain/registry/`) turns a legacy config's bare **name** into a reference to a real declaration on load. It adopts them as **globals**, and that is not arbitrary: `action.set_variable` promised a value "readable by later runs and other macros" and the store was keyed by bare name with no scope, so every existing variable already *was* global — adopting as local would sever any pair of macros sharing a counter and strand every stored value. `GlobalVariableRepository.adopt` moves the value across too (`VariableStore.adoptLegacy`), so a counter keeps counting. The repair is idempotent and the repaired graph is **not written back**: writing on load would turn `rearmAll` into a boot-time write storm and race the editor's debounced save.

## Geofence places

Geofences are a **shared library**, not per-node coordinates: `GeofencePlace` records live in `{filesDir}/places/geofences.json` via `GeofencePlaceRepository`, and `trigger.geofence` stores only a place id. The trigger resolves it at activation through `TriggerHost.geofencePlace(id)`. Because a trigger reads its place only when arming, edits to a place fire `MacroEngineService.ACTION_REARM_ALL` so live macros pick up the new location.

**Three of the trigger's four transitions come from Play Services; the fourth does not.** `GEOFENCE_TRANSITION_DWELL` is loitering *inside* a fence and `setLoiteringDelay` is the enter→dwell gap, so there is nothing that means "outside for a while" — and "when I have been out of the house for half an hour" is a thing people plainly want. So `onAway` is an ordinary `AlarmManager` alarm (`TriggerHost.armGeofenceAway` / `cancelGeofenceAway`, `AndroidTriggerHost` over the shared `setWakeup`), started when the exit arrives and cancelled when an enter does, landing back on `GeofenceReceiver` under a second action and going onto the bus as `event = "away"` through the same `emitOrHold` the real transitions use.

Three consequences are written into the code because none is guessable. **`GeofenceConfig.platformTransitions` and `emittedEvents` are two sets**: watching for away means asking the platform for enter *and* exit whether or not the user wants an event on either, so the emit filter moved out of the flow's `.filter` chain into the `collect` body. **The countdown deliberately outlives the arm** — `GeofenceReceiver` asks for a re-arm on every transition, so a countdown cancelled in the trigger's `finally` would be torn down by the very exit that started it; a stray one is self-cleaning, since the event reaches a node that is not collecting or one whose switch is now off. And **`setInitialTrigger` stays `INITIAL_TRIGGER_ENTER`**: an initial exit would let a macro armed while already away start counting, at the price of a real exit broadcast on every re-arm, which restarts the countdown and fires the `exit` branch of any macro that has one. The limitation that buys — armed while away, counting starts on the next return and departure — is in the node's KDoc.

**That last argument was half wrong, and `GeofenceGate` is what it cost.** `INITIAL_TRIGGER_ENTER` suppresses only the *initial* notification; it does not stop Play Services announcing the state it re-derives after a registration, and an announcement of "outside" arrives as an ordinary `GEOFENCE_TRANSITION_EXIT`. Since `armGeofence` removes and re-adds on every arm, and the process is reaped and resurrected all night by alarms and periodic work, an exit macro fired at three in the morning from wherever it was sleeping — and looked like a fault in the *fence*, because the fix was accurate and the phone really was outside. So the asymmetry users report (exits are spurious, enters are not) is not about location quality at all: it is that you sleep outside the fence you watch, so a state-reset artefact can only be an exit.

`GeofenceGate` (`engine/trigger/`) is the pure decision that fixes it, and the order of its rules is the argument. **Remembering where we were** is the load-bearing rule — persisted in `GeofencePresenceStore` behind `TriggerHost.geofencePresence`, because the artefact fires *because* the process died, so an in-memory belief would be cleared exactly when it was needed. **The accuracy floor** (`max(radius, GeofencePlace.RELIABLE_MIN_RADIUS_METERS)`) is the second line, for a doze-time cell fix kilometres wide; a fix rejected there deliberately teaches nothing, or the next good one is judged against noise. **The contradiction check** (`GeofencePlace.distanceTo` against the radius, widened by the fix's own accuracy) is what keeps the belief from wedging: a fix whose whole uncertainty circle falls on one side outranks anything remembered, so a genuinely missed enter cannot swallow every departure after it. `away` and `dwell` bypass all three — one carries no location and the other is *defined* as still being where we already were. The gate is called ahead of `driveAwayCountdown`, not beside the emit filter, because an exit that never happened must not start an away period either.

The global variable library is this library's sibling and is built from the same parts — a repository read synchronously at construction, an activity-scoped ViewModel, a reusable list, an `EditorOverlay` editor stacked above an `EditorOverlay` picker, a `CompositionLocal` the config form reaches it through, a `PickerKind` branch, and a route reached from the workflow list's top bar. The one thing it does differently is that a variable has *two* scopes where a place has one, which is why `VariableLibrary` is an interface over both halves rather than a ViewModel passed directly.
