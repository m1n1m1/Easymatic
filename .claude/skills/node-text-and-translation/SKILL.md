# Node text and translation

### Node text and translation

The app ships English only, and every user-facing string is nonetheless **resolved through Android string resources**, so adding `values-de/` later is a content task with no Kotlin in it. There are **two routes**, and which one a string takes is decided by one question: *is its answer set closed?*

**Direct `R.string`, wherever the values are a closed set** — `NodeCategory` (`feature/i18n/CategoryLabels.kt`), `PrerequisiteType` and the permission copy, `ValidationIssue`'s reasons, and every string in `feature/`. An exhaustive `when` over an enum is checked in both directions: a new category will not compile until somebody has decided what it is called, and a missing `R.string` fails the build rather than falling silently back to English. This is the same shape as `AiProviderCopy` and `PermissionCopy`, and it is preferred wherever it is available.

**Generated keys, only where the set is open-ended or annotation-bound** — node `displayName`/`description`, `Port.label`, `@Label` config fields and enum option labels. The key is derived from the **`typeId` the declaration already carries**, so the literal stays where it is and no node file is edited: `node_<typeid>_name` / `_desc`, `port_<typeid>_<port>`, `cfg_<typeid>_<prop>` and `opt_<typeid>_<prop>_<value>`, with `NodeText` (`feature/i18n/`) the one place declaration and resource meet. Adding a node still costs one file and one registry line.

Three independent facts force that second route, any one of them sufficient, and they are worth knowing before proposing to "just use resources directly". **`R` fields are not compile-time constants** — `android.nonFinalResIds` has defaulted to true since AGP 8, and `javap` on this project's own `R.jar` shows `public static int` with no `ConstantValue` — so `@Label(R.string.x)` does not compile, and flipping the flag fixes only this one of the three. **`:node-api` has no `android.jar`**, so `NodeCategory.displayName`, `Port.label`, `PermissionRequirement.label` and `NodeSchema.prettify` could hold only an opaque `Int` they could never resolve. And **a plugin compiles against `:node-api` in a different APK**, where its res ids mean nothing in this process — which is why plugin labels already cross the binder as rendered `String`s and why `NodeTypeDefinition` gaining a `displayNameRes` would need the `String` kept anyway. `PermissionRequirement.label` additionally cannot take one because it is a computed getter rather than a parameter.

The keyed mechanism is `PermissionRequirement.rationaleKey`'s, whose KDoc has always described it — generalised, and with the key derived rather than hand-written.

**A missing key falls back to the declaration's own literal**, in `NodeText`, and that is the only such fallback in the app. It is load-bearing rather than defensive: a **plugin** node's text arrives over the binder already rendered by its author, so no key exists for it or ever will. It also covers a node added since the last regeneration, which renders English while the sync test says so.

`prettify` is the reason the generator reads **`ConfigSchemaRegistry` rather than source text or annotations**. By the time a `ConfigField` exists, `labelOr` has already chosen between an `@Label` and `prettify(propertyName)`, and the two are indistinguishable from there — so an annotation scan would miss every prettified label and leave `prettify`'s structural English-only-ness in place. Materialising its *output* into a key is what fixes it, and `prettify` then goes on serving the one case that cannot be materialised: a plugin's un-annotated property. It is a minority of labels rather than a majority — 204 of 247 config properties in `engine/` carry an explicit `@Label`, and only some fifteen or twenty form fields fall through — but a rule that covered all but twenty labels would be worse than no rule.

`res/values/strings_nodes.xml` and `feature/i18n/NodeStringIds.kt` are **generated and committed**, never hand-edited. Committed rather than built, because a Gradle task cannot do it: the declarations are in `:app`'s main source set, so reading them means compiling `:app`, which needs `R`, which would need the generated XML — and `NodeStringIds` naming every `R.string` explicitly sits inside that cycle. Regenerate with

```
.\gradlew.bat :app:testDebugUnitTest --tests "*NodeStringsSyncTest*" -PregenerateNodeStrings=true
```

`NodeStringsSyncTest` is that generator and its guard in one class: without the flag it compares byte-for-byte and names the stale key. `NodeStringIds` is two parallel arrays rather than a `mapOf` of pairs — one `Pair` per entry approaches the 64 KB `<clinit>` limit at this scale — and every id is a literal `R.string` reference so R8 cannot strip it the day `optimization { enable = true }` flips, which matters more than `Resources.getIdentifier` being `DiscouragedApi`-flagged.

The generated files are also **valid while empty**, which is not incidental: a key family is added in the step that introduces it and filled in the step that uses it, so `arrayOf()` sits there with nothing to infer from. `NodeStringIds` declares `Array<String>` and `IntArray` explicitly for that reason. Note too that a regeneration cannot rescue a state where the *resources* fail to merge — aapt runs first, so a duplicate key between the generated and hand-written files has to be resolved by hand before the generator can run at all.

`NodeText` is deliberately **not a `CompositionLocal`**: `GraphEditorViewModel` names a node as it is placed, `MacroSnapshots` and `MacroShortcuts` build widget and launcher labels, and a Glance widget composes where Compose-UI's `stringResource` does not exist. Splitting the `(String) -> String?` lookup out of `Resources` is also what leaves every function pure and JVM-testable, which is how the plugin fallback is pinned without a device.

The Problems panel takes the direct route through a **typed reason**: `ValidationIssue` carries an `IssueReason` plus the values that fill its blanks, and `IssueText` (`feature/grapheditor/`) turns the pair into a sentence. `GraphValidator` stays in `engine/`, which may not reach resources, and keeps building the English `message` as well — because that is what `executeFrom` writes to the run log, which is **not** translated. The two must therefore say the same thing.

**`HardcodedFeatureStringTest` is the guard**, replacing lint's `HardcodedText` (`lintDebug` is unusable here, and a custom detekt rule would mean a new Gradle module plus `detekt-api` carried forever for one check). It scans `feature/` for user-facing literals against a committed allowlist at `app/src/test/resources/i18n-allowlist.txt`. **The list only ever shrinks**: a new literal fails the build, and a converted one has to be deleted from it, so it cannot quietly go stale. It is keyed by file and text and deliberately **not** by line number — wrapping one long line would otherwise churn every entry below it, and an allowlist that needs regenerating on unrelated edits stops being read.

What is left in it is the honest remainder: **interpolated** strings, which need a positional format string rather than a straight swap, plus three in `AiConnectionsViewModel`, which has no `Context` to resolve one with.

Debug builds enable **pseudolocales** (`isPseudoLocalesEnabled`). `en-XA` is how you see whether a string went through resources at all: anything still rendering plain ASCII is still a hardcoded literal, and that check works without reading a word of any translation.

**The app ships English (`en-GB`) plus German, Spanish, French, European Portuguese, Simplified Chinese, Japanese and Russian.** Every `values-<locale>/` is hand-maintained even for the node strings, whose English half is generated — the generator only ever writes `values/`, so a regeneration cannot clobber a translation. `TranslationKeysTest` guards the set: a locale may hold a **subset** of the keys, because a partial translation has to be able to ship and anything missing falls back, but never a **superset** — a key that exists only in a locale is dead, and is almost always a typo. It also pins that a translated string keeps the same `%1$s` placeholders, which is the failure that throws at runtime in one locale only, and so is invisible to anyone developing in English.

**Only `values-de/` has been reviewed by someone who speaks the language.** The other six were produced in one pass each and are unreviewed — good enough to ship behind a language picker the user opts into, not good enough to assume correct when a bug report quotes one. Read a reported string against `values/` before believing what it says, and treat a native speaker's correction to any of es/fr/pt/zh-rCN/ja/ru as authoritative over what is there now.

A locale is **not** written by hand into `values-<locale>/`. The English side is dumped to TSV by `loc/dump.py`, translated as three tab-separated tables (`loc/<locale>.keys.tsv` keyed by resource name, `loc/<locale>.nodes.tsv` keyed by *English value* so one translation covers every node string that says the same thing, `loc/<locale>.plurals.tsv` keyed `name:quantity`), and rendered by `python loc/mkloc.py <locale>`, which owns the XML escaping — `&`, `<`, backslashes and the bare apostrophe that is a **build error** in Android XML. It prints a count of anything still untranslated, and the run is not finished until that count is zero. Doing it by hand is how `%1$s` goes missing from one string in one locale.

`quantity` is per-language and **not** a translation of the English set: en/de/es/fr/pt need `one`/`other`, zh and ja need `other` alone, and **ru needs four** — `one` (1, 21, 31…), `few` (2–4, 22–24…), `many` (0, 5–20…) and `other` (fractions). `TranslationKeysTest` deliberately does *not* require the categories to match `values/`; it only requires each `<item>` to keep its placeholders. Requiring a match would forbid exactly the thing CLDR requires.

`generateLocaleConfig` is now **on**, which is what puts Ottomatic in Android 13+'s Settings → Apps → Ottomatic → Language. It needs `res/resources.properties` to name what the unqualified folder holds (`en-GB` — the copy is British: "colour", "optimisation", "centre"). It was deliberately off while the app shipped one locale, because it would have published a language picker offering exactly one choice. Note that a **debug** build lists the pseudolocales there too, since they are real `values-*` folders to AGP; a release build lists the eight real ones alone.
