# Asking the user

Four nodes in `NodeCategory.INTERACTION` put a question on screen mid-run and wait for the answer: **Show Message**, **Ask Yes or No**, **Ask for Input**, **Ask to Choose** (`engine/action/`, shared parts in `PromptSupport.kt`). Before them a macro could only ever act on what was already true — "shall I really?" and "how many minutes?" were not expressible, and `action.notify` is fire-and-forget with no buttons and no reply.

**Four small nodes, not one node with an "Art" dropdown.** This is Automate's shape, and the reason is the same one that keeps the three loops separate: a node whose meaning *and* port set both hang off a dropdown is a node whose card tells you nothing until you open it. The cost is that there is no multi-field form — a form is two dialogs in sequence — which is the trade every macro tool on the phone makes. `matchesSearch` searches the category label and typeId as well as the description, so `action.dialog_*` under "Ask the User" answers to *dialog*, *ask* and *user* for free; **popup** is the word that has to be written into each description by hand, and `DialogDiscoverabilityTest` pins all four.

**The answer comes back as a branch, and only as a branch where there is nothing to carry.** `ExecOutputs.DECISION` is `confirmed`/`cancelled`/`timed_out`; `ACKNOWLEDGED` is `out`/`timed_out`, because a message that was read and one that was dismissed are the same event. That is not a second conditional sneaking in beside `action.if`: a comparison still lives in exactly one place, and this routes on an answer that was never a value. `action.dialog_choice` deliberately does **not** grow one exec output per option — Shortcuts' *Choose from Menu* does, and it would make the node's shape depend on a text field — so the pick leaves as data on `choice`/`index` (the words `action.for_each` already uses) and the graph branches on it with the comparison it has.

**`timed_out` is declared always and drawn only when a timeout is set.** All three routes are static, because `routePort`'s `require` checks the declaration and because separating "the user said no" from "nobody was there" is the whole reason for a third branch. But a dialog that waits forever can never take it, and an exec port that cannot fire invites a wire that will never run — so `dialogEffectivePorts` hides the handle at `timeoutSeconds <= 0`, the same "a port exists once it is asked for" rule `action.script` keeps. The consequence needs `pruneRetypedEdges`: `GraphValidator` resolves exec edges against the **static** declaration (`ExecConnection.endpoints()`), so an edge stranded by clearing the timeout would never be reported — it would simply stop being drawn and never fire. It is the only *exec* edge that machinery prunes.

**The timeout is the node's, not the renderer's.** Each node wraps `prompts.ask` in `withTimeoutOrNull`, and the resulting cancellation is what takes the window down — which is also how disabling a macro mid-question dismisses its dialog. `Prompts` therefore has two outcomes plus "not possible", and `askUser` is the one place seconds become milliseconds.

**Text crosses the boundary, types stay in the graph.** `Prompts` lives in `core/service/`, which imports nothing from `domain/`, so it cannot speak `ValueType` — and should not: `PromptFieldKind` says which keyboard, `ValueType` says what the answer *is*. `action.dialog_input` converts what it gets back through the same total `ValueType.convert` the autocast uses, and `dialogEffectivePorts` retypes its `value` port to match (narrowing to a `Long` consumer exactly as `transform.convert` does), so an answer asked for as a whole number drops into a numeric port with nothing in the wire. It is the same boundary `NodeSchema.decode` draws with `asText()` and `ScriptEngine` draws with JSON, and it is safe for the reason the totality rule asks for: the chosen type is visible on the card.

**An unshowable dialog takes the `cancelled` branch and logs at WARN.** Fail closed, like `PhoneRef` on an unresolvable contact: a question nobody could be asked must never come back as a yes. WARN rather than INFO because, unlike a refusal, the user can fix it. Nothing here halts — what "the dialog failed" should mean is an `action.if` downstream, which is visible.

**Rendered as an overlay window, always.** `OverlayPrompts` (`data/prompt/`) shows a `MaterialAlertDialogBuilder` dialog whose window type is `TYPE_APPLICATION_OVERLAY`, serialised behind a `Mutex` so two macros queue rather than stack. An Activity was the alternative and saves nothing: background activity launches are blocked from Android 10 on, and holding `SYSTEM_ALERT_WINDOW` *is* the documented exemption — so an Activity would need the identical grant plus a task switch, a back stack and a rotation lifecycle. `PrerequisiteType.OVERLAY` is the new grant, wired through the three places the accessibility one already goes (`AndroidPermissionChecker`, `PrerequisiteState.openSettingsFor`, `NodePermissionNotice.rationaleFor` — **a requirement with no rationale string renders no card at all**). `adaptiveNode` gained a `permissions` parameter for this: being adaptive is a statement about ports, not about what a node needs to run.

**This is the app's one non-Compose surface, and `com.google.android.material` is here for it alone.** Not a preference: `data/` may not depend on `feature/`, and hosting Compose in a raw overlay window means standing up a lifecycle owner, a saved-state registry and a view-model store by hand, plus back-press and IME plumbing. `MaterialAlertDialogBuilder` *is* the Material 3 dialog — shape, elevation, type scale, button placement, the list layout, the icon slot — so nothing about how it looks is drawn here. Text input is a `TextInputLayout` outlined box and yes/no is a `MaterialCheckBox`, for the same reason.

**It follows the phone, not the editor.** The canvas is a fixed dark palette and this deliberately is not: a window that appears over somebody's messaging app should look like it came from their phone. So `Theme.Easymatic.Dialog` is `Theme.Material3.DayNight` and `DynamicColors.wrapContextIfAvailable` repaints it from the wallpaper on Android 12+; `dialog_accent` is only the pre-12 fallback, where there is no system palette to take. The one Easymatic cue is **the bolt in Material 3's icon slot** — the same bolt the palette draws on a trigger — and it is a *shape*, tinted by the system like everything else: forcing a brand colour into a wallpaper-derived palette is how a dialog stops looking like it belongs to the phone. `ThemeOverlay.Material3.MaterialAlertDialog.Centered` is what stacks that icon above the title, which is the layout the component gives branding, so the one thing that is ours is also the most standard thing about the dialog.

**A list dialog builds its own header** (`dialog_prompt_header.xml`), and that is the platform's doing rather than a styling choice: `AlertController.setupContent` attaches the list *only* where no message was set, so `setMessage` + `setItems` on one dialog shows the question with no options under it — which reads as a broken node. The header references the same M3 icon and title styles the theme hands `setIcon`/`setTitle`, so the four dialogs look alike.

**Known limit:** an overlay does not appear over the lock screen, so with the display off a dialog waits behind it and usually hits its timeout. Reaching somebody who is not holding their phone is a notification's job; a notification presentation mode (buttons + `RemoteInput`) is the obvious next step and deliberately not in this one.

The app's side is unit-tested with a fake `Prompts` (`DialogActionsTest`, `DialogPortsTest`); the window itself needs a device and lives in `androidTest` (`OverlayPromptsTest`), skipped unless the permission has been granted by hand.
