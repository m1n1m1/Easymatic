# AI nodes and the AI tool harness

### AI

Two actions and nothing else — `action.ai_prompt` ("Ask AI"), a chosen model plus text in, text out, over **Gemini, Anthropic Claude, OpenAI, OpenRouter, any OpenAI-compatible server, or Gemini Nano on the phone itself**; and `action.ai_describe`, the same thing with a picture. No trigger and **no value node**: the rule that pairs a trigger with a value takes its second exemption here, since there is nothing to read at rest, and the pull side is for reads that are cheap and cannot fail where this is a billed network round trip. That second clause is the one `value.ha_state` later showed to be about the *transport* rather than the network as such — and it still excludes this one, because there is no cache a prompt could be answered from. `Ai` (`core/service/`) is the facade, reachable from `ExecutionContext` and nothing else, on `Mail`'s and `SmartHome`'s exact reasoning.

**The key is the user's own, and that is the whole architecture.** The alternative — Firebase AI Logic, or a project key shipped in the app — bills every prompt every user ever fires to whoever published Easymatic. That is a manageable bet in a chat app where a human types and waits; it is a bad one here, because the point of this app is that a macro fires *unattended*, and one `action.repeat` around an AI node is a bill nobody chose. A pasted key spends the user's own free tier or credit, is revocable from their own console, and needs no `google-services.json`, no Gradle plugin, no App Check and no SDK for any of the five hosted providers — `INTERNET` was already in the manifest, so there is no `PermissionCatalogue` entry either. **The on-device provider is the one dependency this argument does not cover, and it does not need covering:** `com.google.mlkit:genai-prompt` is an AIDL binding to a system service rather than a client for somebody’s billed API, so it introduces no key, no account and nothing to bill — which is the same conclusion by a different route.

**The library is two levels: a provider account, and the ways of asking through it.** `AiConnection` is the account — a name, an `AiProvider`, a sealed key, an optional address — and an `AiModelProfile` under it is what a node actually points at: a model id, an effort, a persona and a set of tool permissions, named by the user ("Household", "Summarise a mail"). The split arrived on 2026-08-15 and the argument for it is the same one that made the library a list in the first place: *the thing a macro chooses* and *the thing that is billed* are not the same thing. Before it, the tier a node picked was the only thing it could say about a model, so a persona had to sit on the account and apply to every use of it, and what the model was allowed to *do* had nowhere to live but each node separately — four macros sharing one assistant kept four copies of one permission list.

`action.ai_prompt` names a profile through `@Picker(PickerKind.AI_MODEL)`, and **there is deliberately no account field beside it**, on the rule the light nodes state: a scoping field earns its place exactly where nothing else determines it, and choosing "Household" already determines the account. The stored value is a bare profile id — no ref type, no parser, no cached name, since resolving it is a local file read.

**The migration is `adoptSingleKey`'s shape twice over.** `upconvertProfiles` mints three profiles per pre-profile connection (Fast, Balanced, Thorough), each carrying its own legacy model id and a copy of the account's prompt, then blanks the legacy fields. Their ids are **derived** (`AiModelProfile.legacyId` — `<connectionId>#<TIER>`), which is what lets `repairAiRefs` (`domain/registry/`, called from `WorkflowRepository.load` beside `repairVariableRefs`) rewrite a saved node as a pure function of that node's own config: no lookup, and no ordering between the two migrations, which run on different threads. What decides whether the upconvert has run is a **marker file and not "has no profiles"**, because an empty list cannot tell a pre-profile connection from one whose profiles the user deleted — keying on it would put three back on every launch.

`AiConnectionRepository` (`data/`) is otherwise an ordinary library, on `MailAccountRepository`'s shape. **It started as a single key and the reversal is the instructive part.** The first cut argued in its own KDoc that one key per phone was the whole model — nobody has two Gemini keys, so a picker would invent a decision for symmetry. Two things overturned it: a second provider is a matter of when rather than whether, and it is the *library shape* rather than the provider enum that is expensive to retrofit; and **quota is per key**, so separating a macro that fires every five minutes from one that summarises a mail is a real use for two keys with one provider. `AiProvider` shipped with one member and existed anyway, for `SmartHomeKind`'s reason — and **the bet paid**: adding four providers touched no workflow, no node, no schema version and nothing in `core/` or `engine/`.

**Adding a provider is a member, a protocol and a row of copy.** `AiProtocol` (`data/ai/`) is the seam — endpoint, headers, body, `readReply`, `readModels` — with `protocolFor` the one `when` over the enum on the execution path, `RoutingAi` the only class that knows more than one provider exists, and `AiTransport` the `HttpURLConnection` half written **once**. That split is the point: the transport genuinely does not vary (a JSON POST with a key in a header and a ninety-second read), where the format does, so this abstracts the part that differs rather than the part that is the same.

**There is deliberately no `OLLAMA`, `LMSTUDIO`, `VLLM`, `GROQ` or `DEEPSEEK` member**, and that is the reusable judgement here. Every one of them serves OpenAI-compatible `/v1/chat/completions`, so each would be `OPENAI_COMPATIBLE` with a different default host — a member that buys a prefilled text field and costs a permanent branch in every `when` over the enum. What those servers actually need is a **base-URL preset** in the editor, which is `MailProvider`'s shape and where they live. The one mainstream service that would earn a member is Azure OpenAI, whose auth is an `api-key` header plus an `api-version` query parameter rather than a bearer token.

`OpenAiProtocol` is therefore one sealed class with three objects, differing in four constructor arguments. **The token field is the one that bites**: OpenAI wants `max_completion_tokens` and rejects the old name, while vLLM, Ollama and llama.cpp understand only `max_tokens` and *ignore* the new one — an ignored bound is an unbounded answer rather than an error, so nothing reports it. `reasoning_effort` is sent only to OpenAI for the mirror-image reason: a server that does not recognise it usually 400s rather than ignoring it. Both are pinned by a test.

**Anthropic's fast tier sends no `thinking` field at all**, and that branch is not tidiness either: `claude-haiku-4-5` predates adaptive thinking and rejects `{"type":"adaptive"}` outright, while the other two tiers need it — and, thinking coming out of the same `max_tokens` budget as the reply, need Gemini's headroom trick with it. Wrong in one direction it is a 400; wrong in the other it is an answer with no text in it.

It seals under its own alias (`easymatic.ai.v1`) so revoking it never touches mail or a paired bridge, derives `needsKey` on every call rather than storing a flag (`SmartHomeHubRepository.needsPairing`'s reasoning, for the same restore case — the keystore key is never backed up), and **never hands the plaintext to `feature/`**. The editor therefore shows an *empty* key box on a configured connection, with the label saying that means "leave it alone"; a key on screen is a key in a screenshot, a recents thumbnail and an accessibility tree. A one-way `adoptSingleKey` brings the old single-key file across so nobody is asked to re-find a key over a change they did not make; it self-deletes, so a connection deleted later cannot come back.

**Blank is not an answer, and no model is implicitly default.** An implicit default is invisible on the card, so the day a second one is added every existing node would silently keep billing whichever sorted first — which, quota being per key, is a real consequence and not a cosmetic one. `AiConnections` (`domain/registry/`) is the **fourth hydrated registry**, after `MacroDirectory`, `GlobalVariables` and `SmartHomeHubs`, so `validateAiModelRefs` can warn about the unset case, the deleted case and — since the open-ended providers arrived — the **unfinished** one. It publishes *four* sets rather than one filtered list: `exists` must go on seeing a half-finished profile or the panel would call it deleted, which is the wrong sentence about a model sitting right there in the list. Three states, three fixes, three sentences. The unfinished one earns its place most, and now spans both levels — a profile with no model id, *or* one on an account with no server address, renders perfectly in the picker and answers nothing. `hydrateFrom` is where that two-level derivation lives, written once because both callers (`ServiceLocator` and `AiConnectionsViewModel`) need exactly it.

Which fields a provider requires is `needsBaseUrl` / `needsModelIds` / `isConfigured` in `domain/model/AiConnection.kt`, on `MailProvider`'s reasoning: **three layers ask the same question** — the editor's Save button, the Problems panel and the facade before it sends anything — and the first two may not import `data`. A provider's *requirements* are a fact about the library where its JSON envelope is a fact about the wire.

**The editor teaches, which no other credential form here has to.** A mail password and a bridge's link button are things the user already has; an API key is minted in a console most people have never opened, and "paste your API key" silently excludes everybody who does not already know what one is. So the steps are numbered **per provider** — a useful instruction names the button somebody is hunting for — the console opens on a tap rather than printing a URL to be transcribed (the failure a `@Picker` prevents, one layer out), and a paste button sits beside the key field, because the key arrives by clipboard every single time. All of that copy is `AiProviderCopy.kt`, spelled out in exhaustive `when`s rather than read off `@Label`: the cost is that a new member fails to compile until somebody has decided what the screens call it, which is the point. **Test** is not decoration either: without it the first proof a key works is a macro failing quietly at 3 a.m., which is the failure this whole integration is meant not to have. It sends through what is *stored* rather than what is in the box, which is what a macro will actually use.

**Model ids are chosen and not typed, but the field stays editable** — the identifier-picker rule and `@WifiNetwork`'s exception, both at once. A mistyped model id does not fail loudly; it names nothing and the node just looks broken. Every provider here serves `GET {base}/models`, including vLLM, Ollama and LM Studio, so `AiModelCatalog` (a second class over the repository holding the *editor's* needs and no node's, on `SmartHomeSetup`'s reasoning) lists them into a chooser. It cannot be a read-only picker, though, because a listing only offers what this key can reach *right now* and the server being configured is frequently switched off, unactivated, or one that serves no listing at all. The list is a suggestion; the answer set is every model that server will accept.

**A profile carries its own system prompt, combined with the node's rather than replacing it**, profile first, joined by a blank line (`combineInstructions`, in `data/` because that is where the profile can be resolved — `core/` and `engine/` never learn the field exists). The two answer different questions: the profile's is the persona and house rules that should hold wherever that model is used, the node's is the one task. An override would mean any node setting a single task instruction silently threw the persona away, with nothing on the card saying so. Either half alone passes through untouched, which is what makes the field invisible to every macro written before it. **Two levels rather than three** — the account keeps no prompt of its own, because a third layer would be a standing instruction nothing on either screen showed beside the other two.

**`AiModel` names a trade-off, not a product**, and that is load-bearing rather than tidy. Published ids churn on a scale of months, and anything *persisted* that names one becomes a broken reference the day it is retired, with the user having chosen nothing wrong. `FAST`/`BALANCED`/`THOROUGH` outlive them, and the mapping lives in each protocol's `modelId` where a rename is one line nothing persisted notices. Nothing vendor-shaped crosses `core`: the endpoint, the envelope, the key header and the model ids all stop at `data/ai/`, so an on-device Gemini Nano implementation would be a new `AiProtocol` and no edit here, in `engine/`, or in the node.

**It stopped being a node's config when profiles arrived, and the argument came out stronger.** It was a property of every AI node, so a workflow persisted the enum's name — safe, since an enum name does not churn, but it also meant a macro chose between three trade-offs and could say nothing else about the model. It is now `AiModelProfile.effort`, and what a workflow persists is a **profile id the user minted**, which churns not at all — behind which the tier, the published id, the persona and the tool permissions can all be re-decided without touching a macro.

The **per-profile model id** (`modelIdFor`) is the other half and was added when the tables' churn stopped being hypothetical: naming the model turns "wait for an app update" into a text field. `OPENROUTER` and `OPENAI_COMPATIBLE` publish no table at all — a catalogue of hundreds and a machine serving exactly one — so there the id is required. `OpenAiProtocol`'s cross-tier fallback (a blank Balanced borrowing the Fast id) is **gone**, and profiles are why: a profile names exactly one model, so "one machine, one model" is one profile and there is no second field for a blank one to borrow from.

`AiTarget` (`data/ai/`) is the account-and-profile pair every protocol function takes. One parameter rather than two because every question needs both halves and neither is meaningful alone — the address, key and provider come from the connection, the model id and effort from the profile — and passing them separately is how a body eventually gets built for one profile and sent to another account's endpoint.

**Thinking tokens are drawn from the same budget as the reply**, and this is the one genuine trap in the API — a node asked for a 200-token answer can spend all 200 thinking, stop at `MAX_TOKENS`, and return a candidate with **no text in it**, so the limit appears to do the opposite of what it says. Every tier therefore gets a fixed headroom *added on top* of the user's limit (`thinkingHeadroom`), so "longest reply" goes on meaning the reply. Generous on purpose: `maxOutputTokens` is a **cap and not a target**, so headroom the model does not use costs nothing where headroom it needed and did not get costs the whole answer.

**Gemini 3 replaced `thinkingBudget` with `thinkingLevel`, and sending both is a 400** rather than a preference the server picks between — a test pins that the legacy field never reappears beside the new one. The consequence that matters more: **thinking can no longer be turned off.** `minimal` is documented as matching "no thinking" for most queries and explicitly does not guarantee it, so the fast tier is now the *least* thinking available rather than none, and the headroom that used to be needed by two tiers is needed by all three.

**The model table has been broken twice, in two different ways, and `modelId` names only stable flash-family ids now because of it.** First `gemini-3-pro-preview` was shut down — a `-preview` id is one Google withdraws on its own schedule. Then the 2.5 family stopped being offered to *new* keys while continuing to work for existing ones, which is the nastier failure: nothing changes on the developer's phone and every new user gets an error. So: no preview ids, no 2.x ids, and no pro tier a free key may not be entitled to — three stable ids in capability order (`3.5-flash-lite`, `3.5-flash`, `3.6-flash`), differentiated by `thinkingLevel` as much as by model. Both rules are pinned by a test. This churn is precisely what `AiModel` naming a trade-off buys: the table moved twice and no persisted workflow noticed either time.

That the error was *diagnosable at all* is `readReply` reading `error.message` before anything else — "no longer available to new users" is the server's own sentence, and an HTTP 400 alone would have said nothing about which of a dozen things was wrong.

**Text out and not a struct.** A struct carrying the answer beside a status would be closer to `action.http`, and would put an `action.break` in front of every single use for a field most macros never read. The failure is reported where a failure belongs — the run log — and lands on the node's "If it fails" fallback, then pulses `out`: `action.script`'s and `transform.json_read`'s contract, for their reason. A **truncated** reply is the one case that is neither: it is real output a macro will happily send on, so it reaches the port and the console says it was cut off, because silently passing it makes a sentence that stops halfway look like the model's own idea of an answer.

Every protocol in `data/ai/` is pure and JVM-tested for `WebUrl`'s and `MessengerLink`'s reason: the interesting half is *what a response means*, and a refused key, an exhausted quota or credit balance, a blocked prompt, an empty candidate and an answer cut off at the bound are all real shapes that cannot be produced on demand from a live server. All three read `error.message` before anything else, because that sentence — "API key not valid", "Your credit balance is too low", "The model `llama-3` does not exist" — is the one the user can act on where a status code reads as generic failure; the last of those is the commonest self-hosted mistake there is. `AiTransport` owns the HTTP rather than using `SystemServices.httpRequest` for exactly one reason, and it is not architecture: that facade reads with a 15-second timeout, right for an API call and wrong for a generation, and raising the shared one would slow every `action.http` in every macro to suit this node.

**A blank field is refused before the network, not after** (`AiProtocol.configurationProblem`). A self-hosted connection with no address otherwise reaches the transport as a malformed URL, comes back as the same `-1` a dead network gives, and is worded "check the phone's connection" — sending somebody to look at their Wi-Fi over an empty box in this app.

**Cleartext HTTP is permitted app-wide** (`res/xml/network_security_config.xml`), which is the one security decision here worth stating plainly. A model server on the user's own network is reached at `http://192.168.1.5:8000`; there is no certificate a LAN address could present, `network_security_config` needs literal hostnames written at build time, and `NetworkSecurityPolicy` is a process-wide read-only fact with no per-host runtime opt-in — so the choice was this or making the commonest self-hosted setup unreachable without a reverse proxy. `action.http` gains the same reach, which is a gain rather than a cost. The exposure it does open — an API key sent in the clear to an `http://` address across the internet — is met by a warning in the editor whenever the address is cleartext (`AiBaseUrl.isCleartext`), because only the user knows whether the far end is their living room.

`AiBaseUrl` (`domain/model/`) is a second URL reader beside `WebUrl` rather than a reuse of it, and the reason is exact: `WebUrl`'s one rule is *add https*, right for a browser address bar and wrong for `192.168.1.5:8000`, which it reads as host-plus-port, prepends `https://` to, and turns into a TLS handshake error that reads like the server being down. So this one **refuses a scheme-less address** and says which two schemes it wants — because unlike the web, both are ordinary here. It also strips a trailing `/chat/completions`, the likeliest mistake this field will ever see.

### AI on the device

`AiProvider.ML_KIT` is the sixth member and the first that reaches no network: Gemini Nano through ML Kit's GenAI **Prompt API** (`com.google.mlkit:genai-prompt`), which takes text or text-and-one-picture and answers text. It is a member on precisely the ground the enum's own KDoc refuses one to Ollama — those *are* `OPENAI_COMPATIBLE` with a different host, where this one has no endpoint, no envelope, no header and no key at all. `protocolFor` therefore answers **null** for it, which is an assertion rather than a hole: a stub `AiProtocol` would have to invent five URLs and a JSON body for an AIDL call, in the one file whose whole value is that it is pure and JVM-tested.

**The seam is one level up, in `RoutingAi`.** `Resolution` gained an `OnDevice` arm beside `Ready`, and `resolve` branches on `AiProvider.isOnDevice` — a property beside `needsBaseUrl` and `needsModelIds`, for their reason, so a second on-device engine is one line rather than a member named at four sites. The branch sits **before the key guard**, which is the thing that was easiest to get wrong: an on-device connection has never had a key, and `unreadableKeyText` would otherwise send somebody to paste one in again. `AiProvider.needsKey` is derived from `isOnDevice` rather than declared, because the two can never legitimately disagree.

**The pure half stays pure.** `mlKitPlan` and `onDeviceProblem` (`data/ai/OnDeviceAi.kt`) decide what a request becomes and every reason one cannot run here, with no device present — `audioWireFor`'s shape and its argument, since an absent AICore, a half-downloaded model and an unsupported chip cannot be produced on demand from a real phone. `MlKitAi` (`data/ai/ondevice/`) is the only file in the app importing `com.google.mlkit`; it needs no `Context`, since `Generation.getClient` takes only a `GenerationConfig`.

**The tier buys the model and nothing else**, which is less than it buys on every wire. There, `AiModel` chooses a published id *and* a reasoning budget; here there is one model family and no reasoning knob, so `FAST` asks AICore for the quick variant and both slower tiers for the full one, with one low temperature throughout. A temperature ladder would be a knob pretending to be a trade-off, and a macro wants a reproducible answer more than a varied one. **No `thinkingHeadroom` is added either** — that exists on Gemini and Anthropic because thinking tokens come out of the reply's budget there, and copying it across would silently multiply what every on-device node asks for.

**Every phone that cannot answer is met by `AiModelProfile.fallbackModelRef`**, another profile's id, chosen with a picker for the identifier rule's reason. The re-dispatch is **whole**: `fallBack` starts from the *original* request, so running it through `resolve` again folds in the fallback's own persona and reply limit, and it answers with its own account, key, model id and effort. Nothing is merged, because a merge has to say which half wins per field and every answer to that surprises some macro. **One hop** — a fallback's own fallback is not followed, and a profile naming itself is refused; both are cycle guards, and a loop in an unattended macro is a hang rather than an error.

**`toolsFor` follows the fallback too, and that is not a nicety.** The Prompt API has no function calling, so a tool-enabled node pointing at an on-device profile will always be answered by the fallback — and `engine/` builds the tool catalogue from `toolsFor` *before* calling `converse`, so answering the on-device profile's list would build the tools from one profile and run them against another, with no later moment to correct it.

**A failed attempt falls back as well as a refused one**, which is the opposite of the rule every wire provider follows, and the asymmetry is the point: a cloud retry spends somebody's quota on a request that may already have been billed, where an on-device attempt costs no network and no quota at all. That is also what makes a beta artifact safe to depend on — whatever it does that `onDeviceProblem` did not foresee, the macro still gets an answer.

**A fallback that worked is recorded rather than silent.** `AiReply.note` is `truncated`'s argument one step on: every other field on a successful reply says the macro asked and something answered, and which model did — and therefore who was billed — is exactly what a macro quietly moving from a free local model to a paid cloud one must not hide. It is a sentence rather than a flag because the reason is one of six and the node has nothing to add to any of them; both AI nodes log it at INFO.

**The download is the screen's and never a macro's.** `OnDeviceSetup` is a second class over the engine holding the editor's needs and no node's, exactly as `AiModelCatalog` is over the connection library — and the reason is sharper here, because the member it carries fetches gigabytes. A macro meeting an undownloaded model takes its fallback and says so. In the editor the status row stands exactly where the key field does for every other provider, with its own sentence per `OnDeviceStatus` member, and an unsupported phone is stated plainly rather than as an error: every profile on it still works through its fallback, which is the difference between a dead end and a setup step.

**Nothing about this reaches the Problems panel**, deliberately. An on-device profile with no fallback is a legitimate setup on a supported phone, and `AiConnections` is hydrated from the library in `domain`, which cannot ask whether AICore exists. Nor is it a `DeviceCapability`: that axis is declared per *node type*, where an AI node's need for on-device hardware depends on the profile its config points at. The device fact belongs in the two places it is — the status row, and the run log.

### AI tools

`action.ai_prompt` with its **"Let it use tools" switch on** is what turns the app into a **harness**: it hands a model a set of Easymatic's own nodes and macros and lets it read and act until it has an answer.

**It was a second node, `action.ai_agent`, and the merge is what the switch bought.** Two cards reading "Ask AI" and "Ask AI (with tools)" put the same question to the user twice — once by which node they dragged, once by how they filled it in — and once the tool list moved onto the model profile the second card had nothing left of its own. `repairAiRefs` rewrites a saved one into an `action.ai_prompt` with the switch on. The switch **defaults to off**, which is not caution for its own sake: a node placed before profiles existed must behave exactly as it did afterwards — one round trip, no side effects — however much the profile it now points at is allowed to do. Whether the model may *act* is a decision the macro makes visibly, and never one it inherits.

**The permissions live on the model profile, not on the node.** That is the half of the restructure this section is about: the same question answered once for a model is answered once, where the same question answered per node is four copies of one list that drift. `Ai.toolsFor(modelRef)` is the seam — the list crosses from the library as `ToolSpec` text, because `NodeToolRunner` needs an `ExecutionContext` and so must stay in `engine/`, while the list lives in `data/`. Nothing library-shaped reaches `core/`.

**`action.ai_extract` and `action.ai_classify` were built here and removed on 2026-08-15**, and the reason is worth keeping because it is about *scope* rather than about a fault. Both worked, and both were built the interesting way — one tool whose *arguments* are the declared fields, one tool whose single argument is an `enum` of the branches, so the provider itself enforces the shape and `AiProtocol` gained nothing for either. What they were not is *needed*: `action.ai_prompt` already answers structured questions through the same loop, and `transform.json_read` was already the road for a reply that carries shape. A second way to do a thing the graph could already do is a second thing to keep working. If either is ever wanted back, the mechanism to reach for is that one — a single tool whose arguments are the answer — and not any provider's structured-output facility.

Removing `action.ai_classify` took **`RoutedRawAction` / `RoutedOutput`** with it: that contract existed solely so a node could name its own exec port, which nothing else needs. `ExecutionRoute` is a closed enum checked against a declared `ExecOutputs`, so a node with user-named branches would need it again.

**Almost nothing new was needed underneath, and that is the point.** `ExecutableAction.run(node, data, context)` already invokes any action from a config map and touches the graph nowhere; `ValueNode.readRaw(config, context)` needs no node at all; `ConfigSchemaRegistry` already publishes a typed field list per node type, derived from the config class's serialization descriptor; and `trigger.api` already means "run this macro with these named typed values, if it is enabled". `NodeToolCatalog` and `NodeToolRunner` (`engine/ai/`) are the wiring between those and a tool-calling loop. This is the **mirror image of `trigger.api`** — the same door turned inward — and it reuses that door's machinery rather than growing a parallel one.

**A tool is a node type *plus pinned config*, never a node type alone** (`ToolSpec`, `domain/model/`). The obvious design — offer `action.light_control` and let the model fill the fields — collides with *identifiers are chosen, not typed*: that node's `target` is a `SmartHomeRef` spec and `action.ai_prompt`'s connection is a UUID. A model cannot invent either, and a mistyped one does not fail loudly — it names nothing and the node merely looks broken, which is precisely what `@Picker` exists to prevent. So the author pins the opaque fields with the pickers that already exist, and whatever is left over becomes the tool's arguments.

**But a picker no longer *has* to be pinned, and the correction is the interesting part.** The rule was that every `@Picker` field is the author's to answer, on the ground that a model cannot invent a `SmartHomeRef`. That ground is sound and the conclusion was too broad: the fix is not to make the author choose in advance, it is to **stop asking the model to invent**. Where the answer set is knowable, it is handed over as an *enumeration* the provider itself enforces — so "put on whichever scene suits" is expressible, and the model still cannot name anything that is not a scene. `PickerOptions` (`domain/registry/`) is that lookup: one exhaustive `when` on `Suggestions`' shape and for its reasons, including the degradation rule — **empty means "cannot be enumerated", never "there is nothing"**, so a kind nothing can list keeps exactly the behaviour it had.

Which kinds qualify is CLAUDE.md's own test for a read-only picker — *is the answer set knowable and complete?* — asked one layer in: knowable **from `domain`**, with no `Context`, no network and no suspension point. Lights, scenes, HA entities and services, macros and global variables qualify; an app package, a sound URI, a mail account and a geofence place are facts about the phone or about a credential and stay the author's to pin. `AI_MODEL` answers empty **on purpose** rather than for want of a source: letting a model choose which model bills the user is not a gap to be filled. Making the light kinds work needed one thing — `SmartHomeHubs` now publishes each hub's `resources` beside its id, on `HaCatalog`'s exact shape; the snapshot always sat on the hub and only the registry was narrower than what it had. The scope for a scoped picker is the tool's own pinned map, so pinning the hub narrows the entity beneath it and leaving it open widens it, and `ToolPinOverlay` resolves it identically — a form promising a choice the catalogue then withholds is the one way those two could disagree.

**A node adjusts its profile's list, and stores only the difference** (`ToolOverrides`, `domain/model/`). A profile answers "what may this model ever do" once for every macro that uses it; a node answers "and here, what should be different" — one extra tool for this macro, or a field left open so the model picks the scene. Three shapes, one line each: an entry replaces the profile's (which is both *re-pin* and *add*), and `-typeId` refuses one. Storing the *effective* list instead would freeze the profile at the moment that node was last edited, so adding a tool to the profile later would reach every node except the ones somebody had adjusted — the exact surprise the profile split removed. A line **replaces** rather than merging pin-by-pin, which is forced: merging cannot say *remove this pin*, and removing a pin is what this exists for.

It is the same page in both places, with `baseline` the only difference: the checkboxes show the effective list either way, and only the *writing* side differs, `ToolOverrides.between` computing the diff so a row ticked back to the profile's state contributes no line at all. **Reset is not unticking** — unticking a granted tool writes a removal, resetting drops the node's line so the row follows the profile again. The two leave the same effective list today and differ entirely the next time the profile is edited, which is why they are separate affordances rather than one.

The node may **widen** as well as narrow: the profile is a default, not a ceiling. The safety story is unchanged in substance, because it was never "the profile is a sandbox the node cannot escape" — it was *the author decides, visibly*, and a node-level override is the same author deciding on the card, where the run log will name what happened.

**The editor is a checklist over everything, not a list of what was added** (`feature/ai/ToolPermissions*.kt`), and that shape is what the request behind it was actually about: turning every tool on or off has to be one gesture, which a list you build a row at a time cannot offer at any level. So the whole candidate set is on screen — `canRunAsTool`, the same filter the palette was restricted to when tools were picked individually — grouped by the palette's own `NodeCategory`, with a tri-state switch per group and one above them all. A row that is ticked but still carries an **unpinned picker** is badged rather than refused: a switch that would not move until a hub had been chosen makes the one-tap gesture impossible, so the row says what is left to do and the header counts it. That badge replaced `GraphValidator.validateAiToolRefs` and its two `IssueReason` members outright — a tool list is no longer part of a workflow, so a Problems entry about one would point at the canvas, where there is nothing to change.

**The cap stopped being silent** at the same time. `ToolSpec.parse` used to `take(MAX_TOOLS)`, which was survivable while a list grew one row at a time and a lie the moment a switch could tick seventy at once. Now `parse` keeps everything, `MAX_TOOLS` is high enough to cover "allow everything" with a test pinning that as nodes are added, `NodeToolCatalog.build` reports through `onDropped` what it leaves out, and the editor warns well below the ceiling — at roughly two dozen, where a list starts costing more context than the question. The ceiling is the runaway guard; the warning is the advice.

**Three tiers, and macros are the top one.** Value nodes are safe by construction (pure, cheap, no exec ports) and cost nothing to offer; action nodes have real effects; and any macro carrying a `trigger.api` node is callable by name, its `@Ports` spec already *being* the tool's parameter schema. The macro tier is what makes this a harness rather than a gadget: "get the house ready for bed" is one tool call against something the user already trusts. It had briefly become unreachable when the tool list was a form you added rows to; the category-grouped checklist gave it the home it lacked, as a **Macros** group from `MacroControl.callable()`.

**A macro tool answers "ran" or "failed", not data.** `runFromTrigger` returns a `Boolean` and a macro has no return value; anything a called macro computes comes back through a **global variable**, which the AI can read for itself with the `value.variable` tool.

**The loop lives in `data/ai/` and the tool vocabulary in `core/`.** `AiTransport` is written once because the transport does not vary, and the same holds for the loop (post → read → run → append → repeat) while the envelope differs wildly — so `RoutingAi.converse` owns the loop and `AiProtocol` grew `conversationBody`/`readTurn` beside the existing pair rather than replacing it. Keeping the old pair is what leaves every existing envelope test meaningful.

**`AiTurn` (`data/ai/`) exists because `AiReply` provably cannot do the job.** A reply carries text, an error and a truncation flag; a turn additionally carries the tool calls *and* the assistant's own turn verbatim, which Anthropic and OpenAI both require echoed back. Anthropic is the strict one — interleaved thinking blocks must round-trip, and `readReply` deliberately *discards* them so one is never read as the answer. A loop built on the existing reader would drop exactly what it must return. Related trap: all three protocols correctly treat blank text as a failure, and a tool-calling turn has null or absent text on OpenAI and Gemini, so `readTurn`'s blank-text branch is conditional where `readReply`'s is not.

**`AiToolDepth` (`engine/ai/`) is the only thing counting recursion.** A macro tool runs another macro through `runFromTrigger`, which mints its own `Run` with its own `onPath` — so the executor's cycle guard, which is per-run by design, sees nothing. It caps nesting at two *and* refuses a macro that is already in flight, because a macro calling itself is a loop at depth one and would otherwise run twice before anything objected. `AiToolLimits` caps turns and wall-clock the way `MAX_ITERATIONS` does, and hitting either is reported rather than silently truncated.

**A structured answer is asked for with a tool, never with a provider's structured-output facility.** All three providers have one and all spell it differently — a fourth rendering of a thing already rendered three times. Function calling is the same feature from the other end: a single tool whose *arguments* are the answer gets a schema every provider already enforces, over the loop that exists anyway, with nothing added to `AiProtocol`. That is how the two removed nodes worked and how a replacement should.

**`action.ai_describe` is the one that needed something of the platform.** It brought `Files.readBytes` — Base64 rather than a `ByteArray`, because that is the form all three providers want and holding both would double what a foreground service carries — plus one image rendering per protocol. Each keeps the string form of a user turn when there are no images, so every request written before images existed renders byte for byte as it did. A file whose name names no known picture kind is refused *before* the network, because every provider requires the media type and a guessed one comes back as a generic 400 naming neither the file nor the reason.

**Tool names and descriptions are English**, unlike everything else user-facing. `NodeText` lives in `feature/`, which `engine/` may not reach — but the constraint and the right answer agree: this text is read by a model rather than shown to a user, and it is the same choice the run log already makes. `AiTool.sanitizeName` exists because a typeId contains a dot and every provider's tool-name grammar rejects one.

**Every tool call is written to the run log as it happens**, at INFO with its arguments, and that is the only record anywhere of what an unattended macro let a model do. There is deliberately **no confirmation prompt**: the point of this app is a macro that fires unattended, and a dialog nobody is there to answer would make the feature useless rather than safe. What makes it safe is three things, each visible in a different place: the author chose the tools *on the profile*, decided per field what is fixed and what the model may pick *in the pin form*, and switched tool use on *on the node*.
