# Identifiers are chosen, not typed

**A contact is a reference, not a snapshot**, so changing a number in the Contacts app changes it in every macro that points at that person rather than leaving them all dialling a number picked months ago. `PhoneRef` (`domain/model/`) parses the spec exactly as `VariableRef` parses `g:<id>`: `contact:<key>|<name>`, and **anything without the prefix is a literal number** — which is what makes every workflow written before this keep working with no schema bump and no repair pass, and what keeps a number that is in nobody's address book expressible at all. The **display name is cached inside the spec**, and that is not laziness: a contact picker's grant is transient and dies with the task, so without it the field would render an opaque lookup key to anyone who has not granted contacts access — the exact failure a picker exists to prevent. It is display-only and never resolved against, so a stale name cannot dial the wrong person. The **lookup key**, not a row id, is what is stored: it re-resolves through contact merges and re-syncs, where a data-row id is minted afresh whenever a number is deleted and re-added — i.e. it would break in precisely the case the reference exists to cover.

**Choosing needs no permission; resolving does.** `ACTION_PICK` hands back its one row under a transient grant, so the editor asks for nothing. `Contacts` (`core/service/`) is the facade that resolves one when a node runs — its own facade because `SystemServices` is write-only and `DeviceState` is for cheap synchronous properties, not a provider round trip that fails outright on a missing permission. It is action-only *provably*: reading a contact needs a permission and a value node may declare none. The trigger side reaches it through `TriggerHost.contactNumber`, the way `trigger.geofence` reaches its place — but resolved **per event rather than per arm**, because a filter is only a predicate where a geofence has to be *registered* with the OS, so an edit takes effect with no re-arm signal to invent. It **fails closed**: an unresolvable contact matches nothing, because a filter that widened to "any sender" would run the macro on every text from anyone. Comparing two numbers is `PhoneRef.matchesNumber`, never `==` — an SMS arrives as `+43…` while the address book holds `0676 …`, so the old exact comparison never matched at all.

**Actions can declare permissions now.** `actionNode`/`effectNode` gained a `permissions` list; before that only triggers could, which is why `action.call` silently returned false without `CALL_PHONE` with nothing anywhere saying why (and why `trigger.sms` never declared `RECEIVE_SMS` either). `NodePermissionNotice`'s wording branches on `NodeKind`, because an action does not "fire". `READ_CONTACTS` is the one requirement **not** declared on any node: it depends on what the user put in the field, and an amber card demanding address-book access from somebody who typed a literal number is a card people learn to scroll past — the same failure as a warning nobody can see. `usesContacts(node)` (`domain/registry/`) derives it from the config instead, alongside `macroRefKeys`/`phoneRefKeys`, all three built the way `variableRefKeys` already was.

**Two app pickers, not one**, because the two fields ask different questions. `action.launch_app` wants apps that can actually be *opened* — offering a package with no launcher activity is offering a guaranteed failure — while a notification or install filter wants any package, including the non-launchable services that post most notifications, and accepts "any app" as an answer. A `PickerField` receives only the kind, so one kind could not know which default it was under. `QUERY_ALL_PACKAGES` stays and no `<queries>` element is added: `<queries>` can only describe *intents*, so it cannot express "every package", the permission is already declared and already load-bearing for `getLaunchIntentForPackage`, and the two would be redundant. (If Play policy ever forces the issue, the fallback is `<queries>` with MAIN/LAUNCHER, which degrades the filters to launchable apps only.)

**Neither the app list nor the macro list gets a ViewModel behind a `CompositionLocal`.** Those locals exist so a picker can *edit* its library and see its own in-flight edits; neither of these is editable from a config form. So the app list is a process-wide cache (`InstalledApps`, invalidated by the `PackageReceiver` that was already listening for installs) loaded asynchronously behind a mutex — the one library with no cheap synchronous read, so a spinner on first open is the honest answer where `GeofencePlaceRepository` reads its file in its constructor to avoid exactly that. The macro list is a `MacroDirectory` (`domain/registry/`), the sibling of `GlobalVariables` and hydrated for the same reason: `GraphValidator` must resolve a macro id from a pure function that can neither suspend nor hold a repository. Its `isHydrated` flag is load-bearing — empty and *unasked* are different states, and a directory that answered "not found" to everything would report every macro reference in the graph as dangling. The picker lists the workflow being edited rather than hiding it, marked `· this macro`: `action.disable_macro` pointing at itself is the "run once, then switch me off" pattern, and excluding it would delete a capability to prevent a mistake that is not one.

**`@IntentChoice` is the third source an answer can come from**, and it is why "chosen, not typed" is not the same axis as "who owns the answer set". `@Picker` reaches a library of the *user's*, `@PluginChoice` a list of the *plugin's*, and this reaches **whatever app on the phone answers the question** — a gallery, the camera, a document provider, a barcode scanner. It generalises what four fields here already do one at a time: `PickerKind.SOUND` launches `ACTION_RINGTONE_PICKER` and reads `EXTRA_RINGTONE_PICKED_URI`, `@PhoneNumber` and `@ContactName` launch `ACTION_PICK`, `@FilePath` launches `OPEN_DOCUMENT`. Each was a hand-written launcher, intent and result-to-string conversion, and a fifth would have burned a `PickerKind` on a chooser this app does not draw.

**Those four are also the shape of every example**, deliberately: the requests worth declaring are the ones Android itself answers — `OPEN_DOCUMENT`, `CREATE_DOCUMENT`, `OPEN_DOCUMENT_TREE`, `RINGTONE_PICKER`, `ACTION_PICK` on contacts — which work on every phone and cost no permission at either end. A QR scanner is **not** among them, because scanning is not a platform capability at all: there is no system action, and `com.google.zxing.client.android.SCAN` is one app's contract, so the field degrades to a text box on any phone without it. A camera needs both an app and this app's `CAMERA` grant. Both stay expressible and neither is an example, since an example is what gets copied.

It is **editable**, joining the family on `@FilePath`'s argument rather than by analogy: a chooser can only offer what exists *now*, so a picture a previous run wrote is unreachable through one, and the field has to stay `@Wired`. What it stores is legible for the same reason those five are — a path, a scanned code, a URL — with the one exception of a `content://` row id, which `IntentRequests.displayName` resolves under the field the way `SoundPickerField` already resolves a sound's name.

Two consequences follow from *who* draws the chooser. It is the **only widget besides `@PluginChoice` a plugin may declare**, on the exact inverse of `@Picker`'s refusal — a plugin could have asked the same app itself, so withholding it protected nothing. And **durability becomes the declaration's problem**: `ACTION_GET_CONTENT`'s grant dies with the editor's task while `ACTION_OPEN_DOCUMENT`'s is persistable, so the first gives a field that works while the editor is open and then fails silently forever, which is precisely what `persistAccess` exists to prevent one field along. Reach for `OPEN_DOCUMENT`.
