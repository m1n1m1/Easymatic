# The run log

Every workflow has a **console** in the editor, the second item of the bottom bar. It is the only place a `console.log`, a failed action or an unreadable JSON path is visible in the app; before it existed, debugging a script meant a cable and Logcat.

`ExecutionContext.log(message, level = INFO)` is the single entry point, and `DefaultExecutionContext`'s `logger` is a `(LogEntry) -> Unit` that `ServiceLocator` fans out to `RunLogStore` (`data/log/`) *and* Logcat. One store per process, keyed by workflow id — which is what makes a background run from `MacroEngineService` show up in the editor's console with no wiring between them, since both already share one `ExecutionContext`. Giving the service an `android:process` would silently break that.

**Attribution is a scoped copy of the context, never a mutable field.** An action never receives its own `WorkflowNode`, so it cannot attribute its own logging; `WorkflowExecutor.pulse` hands it a context already stamped via `scoped(LogSource(...))`, and every plain `context.log("…")` in every action file picks up its node for free. It must be a copy because the executor recurses and trigger flows run concurrently. `LogSource` carries the *whole* attribution — workflow, run id, node — in one call on purpose: Kotlin's `by delegate` generates forwarders for every member, so a two-step `forWorkflow` + `forNode` API would have had the second call delegate to the *unscoped* context and silently drop the first, leaving every line with no workflow id and the console empty. `ExecutionContextScopeTest` pins this.

**Levels are the contract.** `DEBUG` is the trace level — every value read, every transform, the `→ node` line that is the only record a node ran at all (which is what makes a macro silently stopping at an `action.if` diagnosable), and the `in`/`out` lines carrying the data that crossed it. Those last are what turn "which nodes ran" into "why did this come out": a wire that silently carried nothing, a number that arrived as text, a JSON path that matched the wrong field. Only *wired* data appears — a field typed into the form is already on the card. Values are rendered with `Item.asText()`, so they read exactly as they would in a notification, and a value is shown **whole** whenever the line has room for it — the only cut is the line's own 2 000-character budget, shared out by `WorkflowExecutor.valueBudget`. It shares by **water-filling**: the port names, separators and cut markers come off the top, then every value that fits under its share gives the remainder back, so an SMS struct spends the budget on the body rather than splitting it three ways with a sender and a timestamp that need thirty characters between them. `MIN_VALUE_CHARS` is the floor when a dozen ports share one line; overshooting it leaves the sink to trim the tail. A fixed 200-character per-value ceiling was what this used to be, and it was wrong for one reason: `LogEntryOverlay` exists to show a long line in full, and it can only show what was recorded — an `HttpResponseItem` body is bounded by the line the console can display, not by a ceiling far under it. `INFO` is what a node meant to say: `action.log`, a variable write, a script's `console.log`. `WARN` is degraded, `ERROR` is broken. The console defaults to INFO with an All/Info/Problems filter, and the store keeps DEBUG regardless, so widening the filter reveals history instead of demanding another run.

**Everything is bounded twice** — 500 entries per workflow, and `RunLog.MAX_MESSAGE_CHARS` (2 000) per entry, both enforced in `RunLogStore.record`. The count alone bounds nothing: `action.log`'s message is `@Wired`, so an HTTP body pointed at it is one arbitrarily long INFO line. Capping at the sink rather than at each call site is what makes the limit hold for the next writer too, and it is what lets a writer hand over everything it has. The constant lives in `core/service/RunLog.kt` rather than in the store because the executor sizes its `in`/`out` values against it, and two constants that must agree is the pair that drifts — invisibly, since a value trimmed short never reaches the cap. On disk this works out at ~225 KB per workflow, and a deleted macro's file goes with it (`WorkflowListViewModel.delete`).

**Persistence is INFO and above**, one JSON-Lines file per workflow in `{filesDir}/logs/`, appended on a 500 ms debounce on `appScope` and compacted at twice the 500-entry cap. Its `Json` sets **`encodeDefaults = true`**, and that is load-bearing rather than tidiness: `LogEntry.atMs` has a default, so without it the timestamp is never written, and a restored entry decodes back to its own default — every line from last night reading as "just now", which is exactly the question persistence exists to answer. Nothing fails loudly when it is wrong, so `RunLogStoreTest` pins it. DEBUG stays in memory: it is the bulk of the volume and its value is the live edit-and-run loop, where the process is alive by definition. Reads are synchronous, following `GeofencePlaceRepository` — an async hydrate would render "nothing logged yet" for a frame in exactly the screen someone opens when they already suspect a bug. `attach`'s scope carries the file I/O and must be IO-dispatched; the store does not switch dispatchers itself, which is also what makes the writes reachable from a test.

**The badge is about what is *new*, not about what is *there*.** `consoleProblems` counts WARN and ERROR against an acknowledgement watermark rather than counting them outright, because a badge derived from the whole history goes red on the first bad run and stays red for the life of the log — which is a badge nobody reads, and which makes the *next* problem invisible. `ConsoleBody` acknowledges on every change to the list rather than once on open, so a line that arrives during a run you are already watching is seen too; re-badging the tab the user is standing on would be the same nag in a new place. Nothing is deleted by acknowledging — the WARN is still a WARN under the *Problems* filter, and the badge is only a statement about whether anything is unread.

The watermark is a **timestamp**, in `LogAcknowledgements` beside the store rather than inside it, and both of those are forced. It has to survive the process, and `LogEntry.id` deliberately does not — it is minted fresh on restore precisely so ids from disk cannot collide with ones minted afterwards — which leaves `atMs` as the only identity a restored line keeps. Its own file (`{id}.seen`) because it is rewritten every time somebody opens a console where the log is append-only, and a history that gets rewritten on a read is a history with one more way to be lost. It only ever moves forward (`mark` ignores an older stamp), so a console opened while an older run is still hydrating cannot un-see what a newer one showed. The one cost is a line logged in the very millisecond of an acknowledgement counting as seen, which is the quieter of the two mistakes.

**Deleting one line is `Storage.rewrite`, and clearing is the same call with an empty list.** Removing a line from the middle of a log is the one write that cannot be an append, so it is the only rewrite in the file — and folding `clear` into it removed a second path with its own `pending`/`lineCounts` bookkeeping to keep in step. Three things about it: it `hydrate`s first, so the rewrite is over the whole history rather than truncating the file to whatever this process happened to log; it drops the `pending` batch rather than flushing it, because those lines are already in the buffer it rewrites *from* and flushing would append them twice; and it is synchronous for `clear`'s old reason, since a deletion the user just asked for must not race the debounced write about to append to the same file. It doubles as a compaction, and the only lines it can lose are ones no surface could show — the buffer holds at most the cap, which is exactly what `read` restores. The delete is keyed by `LogEntry.id`, which is what that field is for: two identical `console.log("x")` calls in the same millisecond are equal in every persisted field.

The button for it is in `LogEntryOverlay`, beside "go to the node" and for the same reason: a row is a three-line summary, and a destructive icon on it sits under the finger that was reaching to read the thing. A labelled button under the message it removes is both the confirmation and the thing being confirmed, so there is no dialog on top of it.

**A row is a summary; the line itself lives one tap in.** The store's bound is 2 000 characters, and one of those on a row pushed every neighbour off the screen — so `LogRow` clamps to three lines and ellipsises, and tapping opens `LogEntryOverlay`, an `EditorOverlay` holding the message whole, in a `SelectionContainer`, with a copy button beside it. Selection has to live there rather than in the list: a `SelectionContainer` around a `LazyColumn` eats the taps that open it. That tap is also why "go to the node" moved out of the row and into a labelled button in the overlay — it worked on rows with a `LogSource.nodeId` and silently did nothing on the rest, which is not a thing a row can advertise. The overlay is where the run id surfaces too, since `LogSource.runId` is the only thing that untangles two interleaved runs.

**The day is said twice, in two forms, on purpose.** `consoleRows` (`ConsoleRow.kt`) interleaves a `ConsoleRow.Day` separator into the entries, and every row *also* carries its own date. That is not redundancy: the separator answers "which day am I looking at" while scrolling and says it in words ("Today", "Yesterday") — the two days anyone is actually debugging — while the row's date answers "when was this line" for a row read alone, screenshotted or quoted into a bug report. The forms differ for the same reason: `formatLogDate` spells the month out for the separator and the overlay, `formatLogDateShort` gives the row the locale's numeric form, because a row already carries a clock to the millisecond and often a node name, and the spelled-out month pushes one of the two off a phone's width. Both are localised because it is the *order* of the parts that differs across the eight locales, not just the month's name.

Two things about the separator's placement are subtle and pinned by `ConsoleFormatTest`: `consoleRows` reverses for `reverseLayout`, and a day's separator is emitted *after* that day's oldest line in that order, which is visually above it.

The console collects its flows **inside `ConsoleBody`**, not in `GraphEditorContent`, and they are deliberately not part of `GraphEditorUiState`: `collectAsState` attributes the read to the enclosing composable, so collecting one level up would invalidate `GraphEditorContent` per log line and repaint the whole canvas, since a ViewModel is not a stable type to Compose. The bottom bar keeps that rule — it takes `StateFlow`s and never lists, its two badges collect their own counts, and `GraphEditorContent` collects nothing on its behalf.
